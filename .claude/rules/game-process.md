# Game process

## Game Process Management

- Everything lives in `lib/game-process.js`; nothing in the tool layer spawns processes directly
- **stdout is never piped from a spawn** — this process's stdout carries the MCP protocol. Spawns use `stdio: "ignore"` (or `runChild`'s piped capture) and an `error` handler; never `exec()` inheriting stdio. The one exception is the instance launcher's **stderr**, piped by `spawnDetached(..., { captureStderr: true })` so a launcher that refuses before it writes a `launch.log` can still say why: the stream is unref'd and only its last 4KB is kept. The user's game keeps its launcher's stdio closed, since the Steam client and the game would inherit the pipe and their chatter would read as launcher output
- **Ownership, not names** on Linux (see `instances.md`): `isGameRunning`, `gameStartTime`, `killGame` and `detectActiveProfile` all take the target's config and go through `ownedGameProcesses()`, which scans `/proc` through an injectable reader (`createProcReader()`), so tests feed fake `/proc` data. A process whose stat state is `Z` is not running. Nothing on Linux ever kills or counts a Broforce process by name
- **A user's game this machine cannot see**: `userGameOutOfReach()` names why when `UNITY_INSPECTOR_HOST` is a non-loopback host or the server runs under WSL (`isWsl()`, `isWslRelease()` over `os.release()`; `setWslProbe()` is the tests' seam), and then `isGameRunning`, `gameStartTime` and `detectActiveProfile` answer null and `killGame` answers `unknown: true` naming it, on every platform. The instance is never out of reach
- **Which host**: `127.0.0.1` for the instance; for the user's game `UNITY_INSPECTOR_HOST` when set, else `127.0.0.1`, and on WSL `127.0.0.1` then the default route's `via` gateway (`parseDefaultGateway()`), the next host tried only when the TCP connect itself fails, within the one connect budget. No gateway means only loopback, and the failure's `reachHint()` names the hosts tried, the LAN setting, the Windows firewall and `UNITY_INSPECTOR_HOST`. `detectPlatform()` memoizes the whole detection as one promise, so concurrent callers never see it half done, and the token search, the host choice and `translateScreenshotPath()` await it; `resetDetection()` clears it
- **`runChild()` settles on the child's `exit`**, giving its pipes 250ms to drain, so a command that exits 0 while something it started holds stdout or stderr is judged by its exit; a timeout carries `code: 'ETIMEDOUT'`
- **`/proc/<pid>/cmdline` and `environ` reads give up after 500ms** (`createProcReader()`'s `readTimeoutMs`): they read the process's memory under its mmap lock, which a process stuck in the kernel holds, and each hung read holds one of libuv's four fs threads, so a read that timed out is not asked again for that pid while it still hangs
- **Windows** start time and profile detection ask CIM through PowerShell (`windowsProcesses()`, the script sent as `-EncodedCommand`), since WMIC is off by default on current Windows 11, and fall back to `wmic` when PowerShell cannot answer
- **Under WSL** `launch_game` and `stop_game` refuse the user's game outright, before any detection, since it runs on Windows where this server can neither see nor signal it; an instance target is unaffected
- **Scan cache**: `scanGameProcesses()` memoizes for 750ms per reader, since the crash detector asks twice a second and a `/proc` walk costs tens of milliseconds. `killGame` clears it
- **Bracket trick** (macOS only, where there is no `/proc`): pgrep/pkill patterns bracket their first character *and* the extension (`[B]roforce.*[.]e[x]e`) so the wrapping `sh -c` command line can't match itself. Verify any new pattern with the game closed and confirm a non-zero exit
- `launch_game`: the target decides, and `resolveLaunchCommand()` (async) builds one of five paths. `vanilla` is an option the server carries apart from the arguments: `composeExtraLaunchArgs()` answers `{ vanilla, extraArgs }`, `vanilla` true for `vanilla: true` or `--vanilla` in `launchArgs` before any `--`, and `extraArgs` the tokens with that flag removed; the resolve answers `{ command, args, display, source, vanilla, ignoredArgs, waitsOnExit, prepare, startCauses }`, where `vanilla` is true exactly when the command carries the path's vanilla instruction, which is all `vanillaTookEffect()` reads
  - **1, the instance target**: `<launcher> instance <id> launch [--vanilla] <launchArgs>` from `BROFORCE_INSTANCE_CMD`
  - **2, the user's game with `BROFORCE_LAUNCH_CMD`**: `<cmd> [cmd args] [--vanilla] <launchArgs>`, parsed into command plus arguments; run exactly as configured, and `--vanilla` is the only flag the server adds
  - **3, Windows with no `BROFORCE_LAUNCH_CMD`**: `<SteamDir>\steam.exe -applaunch 274190 <Doorstop> <launchArgs>`; `<SteamDir>` is `reg query` of HKLM `SOFTWARE\WOW6432Node\Valve\Steam` `InstallPath`, then HKCU `Software\Valve\Steam` `SteamPath`
  - **4, Linux with no `BROFORCE_LAUNCH_CMD`**: `<steam> -applaunch 274190 <Doorstop> <launchArgs>`; `<steam>` is `steam` on PATH, else the first of `steamRoots()` holding `steam.sh`, and for Flatpak's root `flatpak run com.valvesoftware.Steam` when `flatpak` is on PATH, since its `steam.sh` cannot run outside the sandbox. `--r2profile <name>` follows a modded launch's Doorstop arguments. `BROFORCE_LAUNCH_TYPE` `auto` is Proton when the game folder holds `.forceproton` or a `*.exe`; Proton's target is `Z:` plus the preloader's real path and `prepareSteamLaunch()` ensures `"winhttp"="native,builtin"` in `[Software\\Wine\\DllOverrides]` of `<steamapps>/compatdata/274190/pfx/user.reg`, keeping `user.reg.bak` when it changes the file, a prefix with no `user.reg` yet being a reply `note`; native's target is the real path and `preflightSteamLaunch()` makes the profile's `*.sh` executable. Both serve a modded launch only. **The pre-flight** runs after the already-running replies and before a `restart`'s kill: the chmod, which is idempotent, or for Proton a read of `user.reg` (a missing file stays the note) and a write check on it and its folder; a failure restores the target and says nothing was stopped. **The write** runs after the kill, just before the spawn, and a failure there says the game had already been stopped. **Before it**, always, the server waits up to `launchTiming.wineserverExitMs` (10s) for no `wineserver` with this prefix as its `WINEPREFIX` (`wineserverHoldsPrefix()` over the proc reader, both paths resolved, since Proton's form is `<compatdata>/pfx/` by whichever path Steam was started with; an unreadable environment counts as another prefix's): a wineserver saves its in-memory registry over `user.reg` as it exits, Proton's `waitforexitandrun` waits for that exit before the game starts, and a stop followed by a launch lands inside that window. The file is read after the wait, so what the wineserver saved is kept. Past the bound the override is written anyway and a reply `note` says it may be lost. A section missing from `user.reg` is appended with no timestamp, which Wine loads and saves back with one. Linux refuses (`LAUNCH_REFUSED`) a Doorstop argument or `launchArgs` token holding whitespace, since Steam splits it at the space, even quoted (steam-for-linux #8315)
  - **5, the protocol fallback** (macOS always; Windows or Linux with no Steam executable): `open`, `cmd /c start ""` or `xdg-open` of `steam://rungameid/274190`. It carries no arguments, so `ignoredArgs` names them and any `--vanilla`, `launch.vanilla` is false and the launch is polled as modded
- **Paths 3 and 4's profile**: `<P>` is `<r2modman profiles>/<BROFORCE_PROFILE>` (`%APPDATA%\r2modmanPlus-local\Broforce\profiles` on Windows, `~/.config/r2modmanPlus-local/Broforce/profiles` on Linux), default `Default`, or `BROFORCE_PROFILE` itself when absolute, its base name then being `--r2profile`. Modded Doorstop 4 is `--doorstop-enabled true --doorstop-target-assembly <P>/UMM/Core/UnityModManager.dll`, vanilla `--doorstop-enabled false`; Doorstop 3 is `--doorstop-enable` and `--doorstop-target`. The version is the major of the profile's `.doorstop_version`, else the game folder's, else 3, and a major over 3 is 4. `BROFORCE_PROFILE` set with no preloader there refuses the launch before anything runs, naming the path and both settings that fix it. Unset, with no `Default` profile or no preloader in it, the user may have Unity Mod Manager installed into the game itself: modded carries no Doorstop arguments and prepares nothing; vanilla carries the game folder's disable argument when the folder holds `winhttp.dll`, `doorstop_config.ini`, or `run_umm.sh` with `.doorstop_version`, and otherwise is not honoured, `ignoredArgs` naming `--vanilla` and the launch polled as modded
- **What the launch waits on** follows `waitsOnExit`. True (paths 1, 2 and 5): the exit is a verdict. A `vanilla` launch is never polled, since Doorstop is off and no inspector will answer: it waits on the launch command's own exit — 45s on the user's game, and on an instance the same 180s budget and cap rules as any other launch, waited out once and reported as the budget actually spent — and reports a non-zero exit as a failure, with an instance's `launch.log` tail where there is one; past the budget the command is left running and said to be. Then the game's process must appear and stay up for 2s within 15s (`confirmGameStarted()`, `launchTiming.startConfirmMs`/`startStableMs`/`startPollMs`), else the launch is `no-process` with the launch tail; where detection is unavailable the reply says the start is unchecked. False (`-applaunch`, paths 3 and 4): started from cold the invoked process may become the Steam client and never exit, so the exit is not waited for, only a non-zero one ends the wait as `launcher-failed`. A vanilla launch goes straight to `confirmGameStarted()` under `launchTiming.steamStartMs` (120s) in place of the 15s, a modded one polls under the same budget in place of the 60s, and `likelyCauses()` adds the path's `startCauses` to the reply: on `no-process` a possible Steam "Allow game launch?" confirmation, and on `no-process` and `connection-refused` the Launch Option that fits, on Linux with a profile, one that is set under Proton or for a modded native game one that is not `linux_wrapper.sh %command%`
- With no game answering and process detection unavailable (`isGameRunning()` null, as for a user's game `userGameOutOfReach()` names), `launch_game` launches and stops nothing and answers `state: "unknown"`, `restart` and `vanilla` included, naming the host from `userGameOutOfReach()`'s reason where it has one, since it cannot rule out a second copy beside a running game. The command is resolved and checked for an executable — a regular file with `X_OK`, by path or through `PATH`, and on Windows only an absolute command, as a file that exists — before a `restart` kills anything, so a launch that could not run leaves the running game alone. A confirmed vanilla game is recorded per target with its start time (`vanillaGames`), and while that game runs `pointClientAtTarget()` gives the client no port and `noPortMessage()` says it was launched without mods, as does `launch_game`'s already-running reply; a stop that left nothing, a later launch, or a game with another start time drops the record. Only the port readback and the inspector poll are skipped. A launch command that exits non-zero ends the wait for either target; a clean exit is the normal hand-off for the user's game and the go-ahead to read `port` for an instance. Spawn failures come back as a tool error naming the command. A `launchArgs` string (tokenized shell-style) is appended to the launch the call runs; the protocol fallback cannot take it and says so. `setLaunchResolver()` is the tests' seam for the resolve
- `stop_game`: on Linux, `<launcher> instance <id> stop` for the instance target and `BROFORCE_STOP_CMD` for the user's game when that is set; otherwise, and whenever either command leaves the game running, SIGTERM to the owned pids and SIGKILL to whatever survives a 3s grace; `taskkill` on Windows, `pkill` on macOS, each followed by up to 5s of the name-based check until the game is gone — one still running then answers `unknown: true`, and one detection cannot see is a stop said to be unchecked (`killGame({ platform, run })` is the tests' seam). "Nothing matched" and "the tool is missing" are distinct results — the latter answers `unknown: true`
- `wait_for_game` and `launch_game`'s post-launch wait share `pollUntilResponsive()` in `index.js`: always at least one attempt, 60s/3s fallback for a non-finite or negative budget, and the call can overrun its deadline by the 5s connect timeout plus the 2s ping floor (`POLL_PING_FLOOR_MS`, above the mod ping's 1s main-thread round trip). Every attempt re-resolves the target's port through `pointClientAtTarget()`, so an instance whose game comes up mid-wait is picked up; with no port to be had the attempt and the final `no-port` state say so instead of guessing at a connection failure. A launch hands its own allocated port in as `launchedPort`, which stands in until the game it started is running and owns it, and no later than `launchedPortUntil`. `connected-unresponsive` means only a ping-stage command timeout (`code` `COMMAND_TIMEOUT`) or an unanswered hello; a non-timeout failure at either is `no-process` when process detection confirms the game is not running, else `connection-dropped`. A handshake refusal ends the poll at once as `handshake-refused`. A launch whose poll runs out in any state but `launcher-failed`, `no-process` and `handshake-refused` says the game may still be starting and points at `wait_for_game`. A `launch_game` restart drops the client's socket and launches only once the kill has seen the old process gone, on every platform, so a game still shutting down never answers the new launch's poll; `wait_for_game` knows of no restart and takes whatever game answers
- **`index.js` shuts down on its own too**: `installShutdownTriggers()`, called from `main()` only so importing tests are untouched, runs `shutdownServer()` once, behind a guard, on SIGINT, SIGTERM, SIGHUP, stdin end, and a stdout `error` (EPIPE from a wrapper that died without signalling it, which would otherwise be an uncaught exception mid-teardown)

## Crash Detection

`sendCommand` polls `isGameRunning()` for the target's own game — `unityClient.gameConfig`, set every time the client is pointed at a target — every 500ms while waiting and answers `"Game process died — the command likely caused a crash"` when the process disappears; when the socket closes or resets first, the reply depends on the game, re-read fresh every 250ms for up to 1s since a crashed game's socket can close a moment before its process leaves the table: gone, `"Connection closed — game likely crashed"`; still running after that second, the mod closed the connection (its server stopped or restarted, or the mod disabled or reloaded); unknowable, a neutral close. A command timeout does not pre-empt that second. Death is declared only after the process was seen alive during that command; where detection is unavailable the command degrades to a normal timeout. A refused connect is worded the same way: `"Game is not running. Use launch_game to start it."` only when detection says so, the listener blamed when the game runs, and neither claimed when detection cannot answer. A `disconnect(reason)` gives the commands it drops its reason: `stop_game`, `launch_game`'s restart, a target switch, a port change and the shutdown each name themselves.
