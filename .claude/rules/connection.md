# Connection

## Handshake

- **The token**: the mod writes `unity-inspector-<port>.token` (`tokenFileName()`) in the game's Unity `persistentDataPath` at every server start, before it listens. `#openSocket()` in `lib/unity-client.js` reads it after the TCP connect completes and before the hello, fresh on every connect, never cached; a completed connect means the file is current. Whitespace is trimmed, and with no file found the hello still goes out with `token: null`, so the mod's reply decides the message
- **Where**, by target, through the `tokenSearch` the client is pointed with (`pointClient()` in `index.js`, beside `gameConfig`): the instance looks in its own `unityDataDir` only, and `UNITY_INSPECTOR_TOKEN_FILE` never applies there. The user's game (`tokenSearch` null, the client's own `steamTokenSearch()`) takes `UNITY_INSPECTOR_TOKEN_FILE` as the file when set, else the newest-mtime readable candidate across `unityDataDirs()` — `$XDG_CONFIG_HOME/unity3d/...` when absolute, `~/.config/unity3d/...`, Flatpak Steam's `~/.var/app/com.valvesoftware.Steam/config/unity3d/...` and `.config/unity3d/...`, `$USERPROFILE` and `~` LocalLow, the Proton prefix's LocalLow, and on WSL every `<automount root>c/Users/*` LocalLow, the root read from `/etc/wsl.conf` by `wslMountRoot()`, `/mnt/` by default (`setWslUsersRoot()` is the tests' seam) — plus `~/Library/Application Support/Free Lives/Broforce`. `playerLogPaths()` builds its Player.log candidates from the same `unityDataDirs()`, so the two searches never drift. The game path and the Proton prefix come from `findSteamGame()`: every library `steamapps/libraryfolders.vdf` lists under `~/.local/share/Steam`, `~/.steam/steam` and Flatpak Steam's `~/.var/app/com.valvesoftware.Steam/.local/share/Steam`, the roots themselves included, and the prefix is `steamapps/compatdata/274190/pfx` of the library holding `steamapps/common/Broforce`, whose `steamapps` it also returns; the macOS log roots and `<gamePath>/Broforce_Data` are log-only and Application Support token-only
- **Outcomes**: `handshakeOutcome()` turns the reply into `null` (accepted) or an error with `code` `HANDSHAKE_REFUSED` and `refusal` `old-mod` (`Unknown method: hello`), `protocol` (a top-level `protocol` beside the error, or an acceptance naming another protocol: when the mod's is higher the message says to update the server, and that a session whose server files are already updated loads them with `restart_server`; otherwise to update the mod) or `token` (any other refusal: the file it came from plus the mod's text, or with no file every directory searched, or the `UNITY_INSPECTOR_TOKEN_FILE` path). Each destroys the socket. `isHandshakeRefusal()` is the test. `HANDSHAKE_PROTOCOL` (1) is shared with the mod. Not refusals: a hello unanswered within the connect timeout (one budget covers connect and hello) is `code` `HANDSHAKE_TIMEOUT`, and a socket closed during it is the usual `Connection closed before it was established`; both carry `stage: 'handshake'`
- **Callers**: `pollUntilResponsive()` returns `handshake-refused` with the refusal's message on the first refusal, never retried to the deadline, and reads a `stage: 'handshake'` failure as the game having taken the connection — `connected-unresponsive` for the timeout, `connection-dropped`/`no-process` for a close. `launch_game`'s already-running check counts a refusal as a running game, answering `alreadyRunning: true, success: false, state: "handshake-refused"` and launching nothing; with `restart` it stops and relaunches as for any running game, and the relaunch's poll then reports the refusal. `sendCommand` rewords only `ECONNREFUSED`, so a refusal reaches every tool, `capture_animations` included, as a tool error carrying its own message

## Timeouts

`commandTimeout()` in `lib/unity-client.js`, keyed by mod command: the mod's worst-case reply for the command plus 2s, where a main-thread action that started inside its `MainThreadDispatcher` budget answers within twice that budget, and one that stops its user code (`execute_code` and the script commands) within its start budget plus its ceiling:
- default 6s — commands the mod answers without a main-thread action (`list_campaigns`), and `ping`, whose main-thread round trip has a 1s budget
- one main-thread action of 5s or less (`game_state`, `inspect_gameobject`, `inspect_component`, `inspect_player`, `list_gameobjects`, `query_gameobjects`, `list_enemies`, `teleport_player`, `set_player_health`, `spawn_entity`, `trace_spawns`, `list_bros`, `set_bro` (the mod command `nextSpawn` sends)): 12s
- `modify_component`: 15s — the write's 5s action, then a 1s action that starts a read one frame later and a 1s wait for it
- `take_screenshot`: 19s — up to 2s waiting for another capture, the 3s highlight action, the 3s action that requests the capture, then up to 3s for the complete PNG
- `go_to_level`: 70.25s — the 3s load request (6s), then the in-play wait: 60s of 250ms polls, the last a 1s action (2s); `restart_level`: 74.25s, the same after a 5s restart action (10s)
- `swap_bro`: 16.5s — the 5s swap (10s), a 500ms pause and a 2s confirmation (4s)
- `set_game_speed`: 17.02s — the 5s write (10s), then 2s reads (4s) for up to 1s, 20ms apart, until two frames have run
- `execute_code`: 29s — one main-thread action that must start within 9s and is given up on 18s after it started; the code is stopped at its next loop iteration or method call once it has run 9s, and reported still running 2s after a stop that did not land
- `execute_script`, `compile_script` (the mod command `compileOnly` sends) and `unload_script`: 57s — one main-thread action each that must start within 10s and is given up on 45s after it started, `Main()` and `Unload()` each stopped once they have run 15s
- `simulate_input`: the plan's own time — each press's `duration` (50ms when 0 or absent) and, between `count` presses, `interval` (200ms when absent); or each action or binding step's duration and every step's `wait` — plus 250ms per press for its frame floors, at most 60s of that, plus 2s, floored at the 6s default and capped at 2³¹−1ms; the initial `simulate_input` request is timed to that budget, and each `input_plan` poll to the budget's remainder, at least 6s, the budget counted from that request's write rather than its time in the queue; the mod answers the request at once and gives the plan's result to the poll that finds it finished, and it answers a request it could not parse with a null id
- connect: 5s

## Cancellation

The SDK aborts a request's `extra.signal` on `notifications/cancelled`, which `wrapper.js` forwards, and sends no reply for it. `handleToolCall(request, { signal })` runs the call inside `unityClient.runCall(signal, ...)`, an `AsyncLocalStorage` scope: aborting drops that call's commands still queued, unwritten, and its command the mod is running, which also drops the socket. Commands the call sends after the abort run normally, so a cancelled `capture_animations` still tears the game down. A cancelled `simulate_input` stops polling at once, its sleep between polls woken, and `#cancelInputPlan()` sends the mod `cancel_input_plan`, under a 1s budget and not waited on, so the call returns at once and `inFlightCommands()` does not count it; the mod stops the plan and releases its keys as for a closed connection, and a budget that runs out drops the socket, which does the same. A plan past its own budget is cancelled the same way. An abort that caught the request or a poll on the socket sends nothing, since that socket's drop already stopped the plan: a cancel runs only on the connection the plan started on, because the mod ties a plan to its connection and plan numbers start over in another game. A cancel goes out behind any command the connection is already running, so the plan stops once that command ends, whether or not that command was cancelled too; a plan already finished answers `cancelled: false`, and a cancel that fails is only logged. One sent after its call was cancelled, as a cancelled run's cleanup step is, polls its plan to the end. `pollUntilResponsive()` checks the signal each attempt and wakes its sleep on it; `launch_game` checks it before the restart's kill, after each of the cap wait's lists and before every relaunch, and wakes its launcher, cap, vanilla, start-confirmation and poll waits, a signal already aborted included; `capture_animations` hands `runCapture` the signal: every wait wakes on it and throws, no further setup command is sent, a cancelled setup releases its claim and a cancelled sweep's `finally` runs the teardown, and the handler's `finally` releases the sweep. `within()` and `pause()` in `index.js` are the waits that wake on it. `run_test_script` hands the signal to `runTestScript()`, whose `simulate_input` step cancels its plan as above, and which sends no step after the abort: it checks the signal after every step and between `until` attempts, and a step's `wait` and its `until` sleeps wake on it. A step whose command the abort cut short (`COMMAND_CANCELLED`, or any throw once aborted) fails with `cancelled: true` whatever its `expect`, and `continueOnFailure` stops there too. The cleanup still runs, unsignalled, so its `until` polls as usual, and the run answers `passed: false` with `cancelled` naming the step it stopped during or after; the SDK sends that answer nowhere, so it is read from the run's `resultsFile`.
