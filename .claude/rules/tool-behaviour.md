# Tool behaviour

## Tool notes

Behaviour the tool descriptions are too small to carry.

- `handleToolCall()` drops a null argument as absent, then refuses an argument key the tool's `inputSchema.properties` does not declare, naming the key and the tool's arguments, and a value its property's `type` or `enum` does not allow, nested `items` and `properties` included, naming the argument, the type and what was sent, all before anything is sent; a `number` must be finite and an `integer` whole, while `minimum`, `maximum` and `minProperties` are left to the handlers. `toolArguments()` reads the schemas from `toolDefinitions()`, the same definitions `buildToolList()` renders. A result whose top-level `success` is false goes back with `isError: true` and its body unchanged, game_state's unanswered-game reply and every mod `{success:false}` included, and a thrown error as `isError` with `Error: <message>`; `run_test_script` steps read the mod's reply through `sendCommand`, so `expect.success` is unaffected
- **A server older than its checkout**: `handleToolCall()` stats the server's code files after every call, and when any changed or vanished since this process started (`performance.timeOrigin`) it appends a second `content` item (`staleCodeNotice()`) naming them, the first item untouched. An error reply is told to `restart_server` and repeat the call unless it may already have acted, as a timed-out command may have; a success reply is told the call ran and not to repeat it, since it may have had a side effect in the game. When `launch_game` moved a session with an instance onto `steam`, which only the child remembers, the notice adds that a restart puts the target back on the session's default; a session whose launcher has no instance mode stays on `steam` across a restart and gets no such line. A restart also ends a live `trace_spawns`, which the server does not track, so the notice cannot say so. State lists and test scripts are read at call time while code is fixed at import, so a server left running across a merge refuses files its newer code wrote. A file's mtime is what counts, and the file list is taken at import, since a new file matters only once an existing one imports it. A rejected call keeps rejecting. `run_test_script`'s steps go straight to `sendCommand`, so only its outer reply carries the notice
- **A main thread that does not answer** is one answer on every tool: `{success: false, error: <text naming the main thread>, mainThreadAnswered: false}`, from one catch in the mod's `HandleMessage`, with no `Internal error` prefix and no stack, so it comes back with `isError`. A reply carrying `error` always carries `success: false`, but for `game_state` and per-component `error`s inside a successful `inspect_gameobject`. `game_state` alone answers a stall as `{mainThreadAnswered: false, error}` with no `success`, a non-error reply: it is the probe a caller uses to learn the game is stalled, and that is its answer
- **`game_state`**: the one gameplay scene is `Test Evan2` and the world map is `WorldMap3D`; `levelName` comes from the campaign file and is null on the challenge maps, which carry none, and `levelNumber` is the number `go_to_level`'s success message names. It has `ironBro`, `instance` is `{id, port, root, stage}`, else an `instanceReason`, and `build` is the running game's store and version, the version asked of the game once per connection until it answers, and never of a game whose main thread did not answer. `campaignName`, `campaignDisplay`, `levelName`, `levelIndex` and `levelNumber` are null whenever `isInGame` is false, since off a level the game still holds the level it left or the one it is about to load. The mod reads everything on the main thread; past its 5s budget the reply is the stall answer above, the server's own fields still with it. `isInGame` is true exactly when the slot tools' level test (`NotPlayingReason`) passes, so it is false at the menu, the world map, the loading screen and the join screen, once the level has finished, while the game counts down to the next scene and while the screen fades to another. `game_state` and `inspect_player` list every slot the game counts as playing (`HeroController.IsPlaying`), with a `state` of `alive`, `dead`, `respawning`, `joined`, `arriving` or `held`, and carry `piloting`; `joined` is a playing slot whose bro the level has not spawned yet — no Player yet, with null `heroType` and `lives`, or a Player before its first spawn — and the slot tools refuse it as `no-player`; `arriving` is a bro with `isOnHelicopter` or `HidingPlayer` set that a start-of-level transport's own list holds (the truck, the drop-off helicopter or the portal), refused as `not-released`, and `held` any other bro with either set, refused as `held`; both read `isAlive: false`, and a piloting bro is neither. `HeroController.BrosReleased` is no part of it, since it stays false for a whole level a mod spawned the bros into without the transport, Utility Mod's custom spawn among them. `playerCount` counts the listed slots
- **Main-thread tools** keep working under the game's pause menu and cutscene pause. Every inspection handler runs on the main thread through `MainThreadDispatcher`, since the game creates and destroys objects there
- **`ping`** answers from the connection's own thread, so it also makes a 1s round trip to the main thread: `mainThreadAnswered` is false, and `frame` null, when the main thread is hung or busy past that
- **`go_to_level`**: a `levelIndex` past the campaign's last level loads the Victory map, and the success message still names the level number that was asked for. The mod's handler (`GoToLevelAndWait`) requests the load, then polls every 250ms, each poll a 1s main-thread action, until the level test passes on a new map holding the campaign and level asked for (the level alone past the campaign's end) with a slot's bro `alive` or the game on `CutscenePause`, and replies `Loaded <campaign> - Level N` with `loaded: true` and `seconds`, plus, when the game is on `CutscenePause` at that poll, `cutscene: "CutscenePause"` and a `warning` saying a cutscene holds the game until a key and that `simulate_input` `start` skips it, nothing pressed: a bro's once-only intro, played when a load spawns a bro in `yetToBePlayedUnlockedHeroes`, freezes a level-start transport with the bro still `arriving`, and on a level whose bro spawns straight in it starts just after the reply instead; after 60s it fails as `not-loaded` with `loaded: false`, the scene and the last reason. `StateModifier.GoToLevel` is the request alone, which `execute_code` calls to observe a load under way. Before the load it closes any cutscene and releases any pause, the menu pause through the game's own toggle and the rest by the game's private `UnpauseGameObjects`, since a load from a pause leaves every object the pause deactivated, persistent ones included, inactive for good. With no player playing, as at the main menu, or no current save, it binds the run to the save slot the game's save menu opens on, else the first other slot holding a campaign that is not an IronBro run, named in `saveSlot`; with none it refuses as `no-save-slot`. `list_campaigns` names are the campaign TextAssets of the game's levels bundle, the only names the game can load
- **`restart_level`** refuses outside a level, with no `GameModeController` and on an online client, where the game's restart would do nothing or only ask the host; it releases a pause as `go_to_level` does and replies once the level is in play again on a new map, under the same 60s wait and with the same `cutscene` answer
- **`set_game_speed`** refuses NaN, negative and above 10. It writes on the main thread and replies with `timeScale` read back once two frames have run since, failing when the game's own time effect changed it: `TimeController`'s slow-motion and the hero time boost rewrite it every frame and set 1 when they end, and `gameTimeEffect` names the one running at the write; a scene load and a cutscene set 1 too, and the game runs its own slow motion on a bro's death, so a speed lasts until one of those. Under the offline pause menu, which holds `timeScale` at 1, it writes only the value the menu restores on close: `timeScale` stays 1 and `timeScaleAfterUnpause` is the speed. The game never stops the clock itself, and several of its methods divide by `Time.timeScale`, `Time.deltaTime` or a unit's `t` unguarded, which a stopped clock makes 0/0 or x/0: Bro Lee's `SetDeltaTime` and `Update`, `TestVanDammeAnim.Jump` (any bro jumping at speed 0), `SortOfFollow.LateUpdate` (the camera shake, whose statics outlive the level), `StatisticsController.Update` (the level's time) and `FallingBlock.DamageInternal` (a crate's or barrel's push). The mod's `FrozenClock` transpiles each, from load on, to divide by infinity in place of a 0, so a stopped clock passes no time there and a running one divides as before; a method whose divisions no longer match the expected count is left alone and logged
- **`set_player_health`**: a value of 0 or less kills the bro through the game's own death path, which costs a life and in IronBro loses the bro from the run, and the reply says `killed`; a positive value on a dead player is refused, as is a piloting player on the kill path, and a bro with a revive halo is refused before the hit, while one the hit leaves reviving fails with that reason. `health` and `playerNum` are integers on every state tool: the server's schema check and the mod both refuse a fractional one rather than round it
- **`teleport_player`**: `z` is ignored, since the game rewrites it every frame, and a reply to a call that passed it carries a `note`; dead, piloting, arriving and held players and points outside the map, compared as floats so 1e30 is outside, are refused, velocity is zeroed, and `playerNum: -1` lists the skipped slots in the reply
- **`wait_for_game`**: a timeout's `state` is `main-thread-hung` (the ping answered with `mainThreadAnswered: false`: the socket thread answers while the main thread runs no frames, so the poll keeps trying to the deadline, and neither `wait_for_game` nor `launch_game` reports ready; a ping without the field counts as ready), `no-process` (no game process is running), `connection-refused` (the process is there but nothing is listening on the port), `connected-unresponsive` (the port accepts connections but the hello or ping got no reply), `connection-dropped` (the port accepted a connection that was then closed), `unknown` (process detection is unavailable) or `no-port` (this session's instance has no running game or port); `handshake-refused` (the mod refused the hello) ends the wait at once
- **Addressing a GameObject**: `inspect_gameobject`, `inspect_component`, `modify_component` and a `take_screenshot` highlight take a `path` or an `instanceId` — a GameObject's, or a component's, which names the GameObject it sits on, so a reference read from a field or `spawn_entity`'s `instanceId` can be followed. A path starting `/` is matched whole; any other matches the end of an object's path, as `GameObject.Find` does. Of several matches an active scene object is taken first, then an inactive one, then a prefab asset, and the reply carries `matches`; every reply names `instanceId` and `scene`, and a prefab asset `isAsset: true`. `modify_component` refuses an asset with `reason: "asset"`, since the write would reach every copy spawned from it, and a highlight on one is a `highlightError`. A prefab asset is a scene-less object with a positive instance id; a live object whose hide flags leave it outside any scene, such as `ApplicationUtility/MonoBehaviourEventCatcher`, has a negative id, reads `scene: null`, is written like any other and is not listed
- **`list_gameobjects` / `query_gameobjects`** list scene objects only — the roots of the loaded scenes and DontDestroyOnLoad, and every object in them — never prefab assets; `scanned` counts scene objects. Each entry carries `instanceId`, `scene`, `isActive` (`activeSelf`) and `activeInHierarchy`. Past `maxResults`, or past about 40,000 characters of entries, the reply stops listing and says `truncated: true` with `truncatedBy` `maxResults` or `size`, while `totalCount`/`totalFound` still count everything. A `maxResults` under 1 is refused
- **`query_gameobjects`**: `namePattern` holding `*` or `?` is a glob over the whole name, otherwise a substring; both are case-sensitive. A `componentType` no loaded type answers to is an error. Types resolve against the assemblies the compiler itself sees: the game's and mods', the loaded scripts', and the latest `execute_code` declaration of each name, never a replaced script's; the resolution is cached until the next assembly loads
- **`inspect_gameobject`**: past the 100-child and 30,000-character caps, `inspect_component` reads a whole component
- **`take_screenshot`**: a highlighted GameObject is outlined at its own renderer bounds, else its own collider bounds, else the combined bounds of its child renderers. One capture runs at a time, its highlight included; a second waits up to 2s. A `highlightError` still leaves the screenshot taken. The capture is requested on the main thread and the reply waits for a complete PNG — its `IEND` trailer — up to 3s. The `Screenshots` folder is created again if it went, and only the newest 50 `screenshot_*.png` are kept. On Linux a game-side `Z:` path is `/` with or without a Proton prefix, and other drive letters go through `dosdevices` of the running game's own Wine prefix (`gameDataLocations()`), else of the Steam library's; on WSL a drive letter goes under the automount root. For the user's game under Flatpak Steam, a path under the home directory, `Z:` or native, is rewritten under `~/.var/app/com.valvesoftware.Steam/`, where the sandbox keeps the game's home, but only when the file is not at the path as given and is at the rewritten one, since a folder granted to the sandbox keeps its host path; the instance target is never rewritten. **`backdrop`** goes as one `execute_code` running the `PlainBackdrop` render (`lib/AGENTS.md`), on that budget and outside the mod's capture lock, writing into the same folder under the mod's naming and keep-50 prune, the folder read from the mod's internal `Main.mod` by reflection. `screenshotReply()` shapes the reply for the tool and a test-script step: `{success: true, path, backdrop}`, the path translated as above (fetched on a remote target, plus `gamePath`); a failed render's error reads `The backdrop render failed: <error>`, with no `position`, `statement` or `stackTrace`
- **`inspect_component` / `modify_component`**: `componentType` and `component` take the type's short or full name, the exact type first and else the first component deriving from or implementing it, as `query_gameobjects` matches; a miss names the components the object has. `suggestions` are the closest paths, qualified with the prefix that resolved. A numeric segment indexes a list or array (`units.0.health`), and a value-type element is stored back like any struct link
- **`inspect_component`**: the whole-component walk lists a static property as `<static property: read it with memberPath>` rather than running its getter, since a getter is game code that can create objects or run a static constructor; `memberPath` reads it. The walk, a detailed `inspect_gameobject`'s included, leaves out a property marked `[Obsolete(…, true)]`, whose getter can log an engine error on every read. A read that throws names the exception's type and message. Values: lists, dictionaries and other collections give `count` and their first 100 items (`truncated` past that), a plain struct or class its instance fields, `Bounds` `{center, size}`, a destroyed `UnityEngine.Object` `{type, destroyed: true, instanceId}`; nesting stops at depth 2 and at 300 values per member with the type's name in angle brackets. Type names are written out with their arguments (`List<Unit>`). The whole component is cut at about 40,000 characters (`truncated`, `omittedProperties`, `omittedMethods`)
- **`modify_component`**: `not-found` is no such field or property on the type, or an index the list does not have, `read-only` one that exists with no setter or is a const field — readonly fields are written — `not-kept` a member that read back different from what was written, and `error` a value that could not be converted (a fraction for a whole-number member included), a setter that threw, or a dotted path that could not be walked: an empty segment, a `shared*` twin that would copy on read, an intermediate read that threw, or a null or destroyed intermediate. A Vector2/3/4, Color, Rect or Quaternion object names only the parts it changes and the rest keep the member's current value; a component quaternion is normalized, an `euler` one keeps the angles it leaves out. Each written member is read back in the same main-thread action into `values` (a member with no getter, or one whose getter would copy, says it was not read back), and once more at the end of the next frame through a coroutine: what changed by then is listed in `reverted` with a `note`, which for a unit's Transform position points at its `X`/`Y` fields. `nextFrameChecked` is false when that frame did not come within 1s or the component was destroyed by then
- **`spawn_entity`**: refused as `no-level` when the slot tools' level test fails, and for a non-finite coordinate or velocity; a success also carries `type`, `prefab` and `name`, and a failure on a missing prefab the resolved `unitType`. A `type` RocketLib's `UnitType` does not resolve is matched, ignoring case, spaces and punctuation, against the prefabs in the game's networked prefab list (`InstantiationController.PrefabList`) carrying `Villager` (`Citizen` derives from it) or `Animal` and no bro; bare `Citizen` takes `Citizen1` when it is `Citizen`-class, else the first `Citizen`-class prefab. Such a spawn's `type` and `prefab` are the prefab's name, `unitType` RocketLib's type of the unit (`Villager`, `Pig` or `RottenPig`) and `networked` false. An unknown name's `availableTypes` lists RocketLib's names, then the unresolved prefab names; its error names the first, and `Citizen` when one is `Citizen`-class. A citizen, unlike RocketLib's plain `Villager`, joins `Map.citizens`, where a bro's high-five looks, on its first `Update`, which it skips off camera. `Mook` units spawn alert and grounded, networked when that list holds their prefab and otherwise through the game's `SpawnMook_Local`, parented to the map and registered as the level loader places them (Treasure Mook, Suicide Bruiser, Strong Bruiser and Brown Mech, `networked: false`); `Facehugger` and `Screecher` go through the game's own local spawn helpers, so they are neither parented nor in the deterministic registry; every other unit is instantiated locally, parented to the map and registered, with `xI`/`yI` as its initial velocity. A mod suppressing enemy spawns (Utility Mod's `disableEnemySpawn`) fails a mook spawn, and the error names the patch owners. `ignoreSuppression` sets `disableEnemySpawn` false and restores it in the same main-thread action as the spawn, so the setting is never saved changed; `suppressionFound` is whether suppression was in force (Utility Mod enabled and the setting on), and null with a `suppressionNote` when Utility Mod, its `enabled` field or the setting is absent and the spawn ran unchanged; a missing field or setting is logged once
- **`swap_bro`** recalls the old bro, costing no life, and is refused while the slot's bro is `arriving` or `held`. In the same main-thread action the slot must then hold the requested bro by its roster name (`GetLiveBroName`, what `list_bros` reports), active, enabled and alive, else `swap-failed` with `currentBro`; 500ms later a second action checks the slot still has the same Player, character and level, and the bro alive, else `swap-undone`. The reply is `broName` (the roster name), `objectName` (the GameObject) and `heroType` for a vanilla bro only, a BroMaker bro's being its preset's base type. The swap leaves the save's `unlockedHeroes` and `yetToBePlayedUnlockedHeroes` as they were, so it unlocks no hero and plays no unlock cutscene. The Swap Bros Mod lookup is made again on every call until it finds the mod.
- **`swap_bro` `nextSpawn`** reaches the mod as `set_bro`, whose reply is `nextBro`, read back from Swap Bros Mod's selection; `appliesThisLevel` is false, with a `note`, when Swap Bros Mod's spawn prefix will skip the selection here: BroMaker spawning a just-unlocked or level-forced custom bro, a versus pick mode, or a level forcing its bros with Ignore Forced Bros off. `ignoreUnlocks` lifts Swap Bros Mod's IronBro unlocked-roster gate (`ignoreCurrentUnlocked`) and replaces its custom bro list with every installed custom bro, locked or disabled included (the names of BroMakerLib's `BroSpawnManager.GetAllBros()`), for the one swap, in one main-thread action, then restores both and every player's selection, the selection even when the restore's `CreateBroList` throws. `customBroCount` is set to BroMakerLib's unlocked count for the swap, which keeps Swap Bros Mod's list refresh from reloading its own list over that one. `ignoredUnlocks.rosterGate` is whether the gate was in force, `ignoreCurrentUnlocked` Swap Bros Mod's setting read back after the restore, `broFrom` where the swapped-in bro came from (`vanilla` for a name in its normal, Expendabros or unfinished rosters, `custom` for one in the custom list the swap used, null otherwise and on a failed swap), `customListReplaced` whether the list was replaced (`source` `GetAllBros`, else `unchanged`), and `note` why not (BroMakerLib absent or unreadable). The IronBro roster-gate half is verified by code trace only, with no IronBro run behind it. In IronBro a swapped-in bro the run has not collected that then dies is added to the run's `hardcoreModeDeadBros` by the game itself (`Player.RemoveLife`), exactly as Swap Bros Mod's own `ignoreCurrentUnlocked` option allows. Swap Bros Mod's own `enableBromaker` (off, its list never takes custom bros, so the replacement has no effect), its `filterBros` filter and its Expendabros/unfinished options still apply. `nextSpawn` with `ignoreUnlocks` is refused: the choice is read at the next spawn, after a restore would already have undone it. An `ignoreUnlocks` swap that is still unreachable names the filter or option that leaves the bro out, never the lock or the IronBro roster it lifted
- **`swap_bro` failures**, `nextSpawn` included, carry a `reason`: `bad-player`, `swap-bros-missing`, `no-level`, `no-player`, `player-dead`, `not-released`, `held`, `piloting`, `unknown-bro` (with `suggestions`), `unreachable` (locked, filtered, or off the IronBro roster), `swap-failed`, `swap-undone`, `swap-bros-incompatible` (a Swap Bros Mod older than 2.2.0, without the `Swap_Bros_Mod.API` members the bro tools need, its error naming the installed version; or one lacking a member `ignoreUnlocks` needs) or `error`; a `nextSpawn` reply also carries `alwaysChosen` before and after
- **`list_bros`** failures carry a `reason` of `bad-player`, `swap-bros-missing` or `swap-bros-incompatible`, the last two as `swap_bro`'s, except an exception, which is an `error` with no `reason`. `currentBro` is the bro actually in the slot (a BroMaker bro's own name, else Swap Bros Mod's display name for its hero type) and `selectedBro` is Swap Bros Mod's selection; both are on each `currentBros` entry
- **`trace_spawns`**: the mod installs one Harmony prefix per target at priority `int.MaxValue` under its own Harmony id, `<mod id>.trace-spawns`, so a prefix that skips the original cannot hide a call, and removes each with `Unpatch(original, prefix)`. Records: mooks `{seq, method, prefab, x, y, xI, yI, time}`, projectiles add `firedBy` (the firer's type name) and `playerNum`, doodads `{seq, method, doodadType, gridPosition: {x, y}, variation, time}`; `time` is `Time.realtimeSinceStartup`. `seq` is one counter across targets and never resets while the game runs. A `start` while tracing re-patches for the new set and keeps the records and the counter; a `start` with nothing traced clears the records; `stop` unpatches and clears them. The disconnect of the connection that started the trace unpatches it and keeps the records for `read`; a `start` or `stop` from any connection is honoured. The server keeps its socket across commands, and `wait_for_game`'s polls and `launch_game`'s already-running check reuse a live socket on an unchanged port. What drops it, and so ends a trace: `restart_server` (a new server process) always; a target switch; a change of the target's port, which includes an instance whose game is no longer ours and so has no port; `stop_game` and `launch_game` with `restart` or a fresh launch; a command that timed out or was cancelled; and a socket the game closed

## list_enemies

The tool is a thin `sendCommand`; everything below is the mod's `HandleListEnemies`.

- **The set**: the union of the game's own unit registry (`Map.units`) and a scene sweep of `NetworkedUnit`, since `Boss` derives from `NetworkedUnit` rather than `Unit` and sandworms never register. Duplicates are dropped by instance id. Entries are kept only when the GameObject is `activeInHierarchy` — `Map.units` holds inactive pre-spawned units, 52 face huggers on `Challenge_Alien` — and only when the unit is not a hero and not a rescue bro, the game's own `IsEnemy` test read from the live `IsHero`, since `IsEnemy` caches its first answer and piloting a vehicle changes `IsHero` afterwards. So neutral characters (villagers, citizens, animals) count while a vehicle a player is piloting does not, dead units the game has not destroyed yet stay listed with `isAlive: false` and `aliveCount` counts the rest, a tank's weapons are units of their own beside the tank, and a `BossTank` contributes dozens of `BossPiece` entries that all report the rig's origin as their position
- **`unitType` and `category`**: RocketLib classifies `Unit`/`TestVanDammeAnim`, so a `NetworkedUnit` that is neither reports both as null; a `Unit` RocketLib cannot classify reports `None`/`none`. `category` comes from a static dictionary built once from RocketLib's eight `UnitTypes` group arrays (`NormalUnits`, `AlienUnits`, `HellUnits`, `BossUnits`, `WormUnits`, `VehicleEnemies`, `FriendlyUnits`, `OtherUnits`) in that precedence — the arrays are disjoint, so precedence is only insurance. A type in no array reads `unknown`, which today is only `Bro`, and `IsEnemy` keeps that out of the list
- **Suppression**, on every reply while a level is loaded, whatever the count: `enemySpawnSuppressed`/`suppressedBy` assert a suppressor is active *right now* — Utility Mod loaded, enabled, and its `disableEnemySpawn` setting on, read by reflection through the mod's settings — so the level loaded with its enemies skipped rather than being empty. The setting skips the mooks, aliens, vehicles and hell enemies a level places but places its bosses, the bone worm miniboss and any enemy the level's triggers reference. `enemySpawnPrefixOwners` is informational: every mod holding a Harmony prefix on the game's enemy placement or runtime spawn methods, `trace_spawns`' own excepted. A prefix may test its own settings before acting, so an owner there is no evidence anything was suppressed
- A failed call answers `success: false` with `error` and no list: an exception, or a main-thread timeout, which adds `mainThreadAnswered: false`

## execute_code Contract

- Input compiles as its own block: statements, local declarations, `return expr;` statements, or a trailing expression as the value. Locals do not persist between calls, so state that must goes in static members or game objects; no lambda wrapping needed
- The tool result is the mod's own object, with three shapes on its top-level `success`: `resultSet:true` with `result`; `success:true, resultSet:false` for ran-but-void; `success:false` with `error`
- A failure from thrown user code also carries `position` (`{line, column}` of the top-level statement that was executing, 1-based in the submitted input) and `statement` (that statement's text). `position`, `statement` and `stackTrace` are all null for plain compiler diagnostics, and absent from a main-thread answer
- `output` is the compiler's messages; `Console.WriteLine` from submitted code reaches the player log, which `read_log` reads, as UMM's console lines do
- **A call that runs too long has three answers**, all `success: false`, the first and last the main-thread answer above: the main thread did not pick it up within 9s, so it never ran and can be sent again (the error names what holds the main thread when it has been held over a second); it ran 9s and was stopped at its next loop iteration or method call (`stopped: true`, with `position` and `statement` of the statement that was running); or it is still running 2s after the stop was requested, which a call inside a game, engine or library method, or a loop the script compiler did not compile, gets, and every later main-thread command waits behind it. The stop is a self-abort the mod's script compiler plants on every backward branch and method entry of code it compiles, `execute_code` input, its declared types and scripts alike, and it lands on every platform; nothing aborts the main thread from another thread
- **Exceptions thrown by submitted code report `stackTrace`**, and reading `StackTrace` or `ToString()` is safe in `execute_code` input and inside a compiled script alike — a script's own `catch` gets a full managed trace naming its methods
- Types defined by a script loaded through `execute_script` are in scope for `execute_code`, by direct name and by reflection over the script assembly (field reads, member enumeration), consts and `null` consts included; an enum declared by a script or by `execute_code` is the exception, and `execute_code` input or a script naming one is refused before it compiles — an enum of a loaded script or of the newest `execute_code` declarations, named unqualified or after its declaring type or namespace, never a member access that only shares its name. A generic method or generic class `execute_code` declares can be used from the same input and every later one, since the mod rebuilds its Evaluator after the declaration. A generic method called from its own compile runs, except with other type arguments from inside its own body, or with fixed arguments to a virtual or interface generic; both are refused naming the rewrite. Code outside the input or script that declared a generic class cannot name its fields, since that kills the game when the method JITs, so it is refused unrun naming the rewrite (a property or a method of the class), while the class's own methods and a script's own code can. A DynamicMethod naming such a field is refused at the emit naming the rewrite, and `AccessTools.FieldRefAccess` on one fails with an `ArgumentException`, both before the method is created. `MethodBase.GetMethodBody()` on a script-compiled method kills the game process, so the mod refuses it in `GetMethodBody` itself, before the runtime reads anything, with a `NotSupportedException`: a direct call and every Harmony patch or body read of such a method get that exception, and a script's `Main()` failure names it when Harmony wraps it. If that guard could not be installed, input naming Harmony or `GetMethodBody` is refused unrun, saying so. Code asking a method or property whose signature names an assembly the game does not have (`JsonConvert`'s XNode overloads) for its parameters, generic arguments or shape, return, property or declaring type, module, flags, custom attributes, method body or `ToString()`, or invoking it, gets the `FileNotFoundException` naming that assembly, and the same reads of one whose signature holds a function-pointer type (Harmony's MonoMod internals) get a `NotSupportedException` saying its `Name` and `MetadataToken` are safe to filter on; either member returned in an `execute_code` result shows as `ToString threw:` with that exception's name. Formatting one as a string inside library code (`string.Concat`, `String.Format`, `StringBuilder.Append`, concatenation, interpolation), or calling its `ToString()` through a generic type parameter, is refused wherever it runs, a script's `Update` included: a member naming a missing assembly throws a `FileNotFoundException`, and one holding a function-pointer type a `NotSupportedException`, its message `Formatting <type>.<member> as a string was refused:` followed by the assembly's name or the function-pointer refusal. If that guard could not be installed, the mod logs so, and formatting a constructor or a property with no getter naming the missing assembly, or a member with a function-pointer type in a method's return type or parameter, a constructor's parameter, a property's type, or the index parameter of a property with no getter, kills the game, while a method or a property with a getter throws a `FileNotFoundException`, since formatting reads its return type first. A loop in a static initializer is stopped too, but answers as the `TypeInitializationException` naming the abort, and that type stays unusable for the rest of the game's run. An exception filter (`catch ... when`) works, and an exception thrown inside the filter replaces the one it was testing rather than counting as false. **Runaway recursion answers as an exception, `RunawayRecursionException` naming it**, thrown at method entry once a call chain has used 512KB of the main thread's stack, whatever compiled code it runs in: `execute_code`, a script's `Main()`, `Unload()`, a later `Update` or Harmony patch, which Unity logs as any other. `finally` blocks and exception filters on the way out run on top of the throw's stack, so they run normally for the first 500ms and 64KB past the limit and are skipped after that, a skipped filter counting as false: recursion without end inside a `finally` or filter, or a `finally` or filter that throws in every frame, ends as an error, and a skipped `lock` or `using` leaves its lock held or its object undisposed. A leading `using` alias repeating one in force compiles as nothing, a preamble alias included; the same name with another target fails with CS1537, with a line saying to pick another name, and leaves the earlier one in force. A delegate declared again replaces the earlier one, as a class does. A stop runs the compiled calls of the `finally` and `catch` blocks it unwinds through for 500ms.
