# Log Files

`resolveLogFile()` in `index.js` picks the file for `read_log`; every response carries `path` and `modifiedAt`.

- **Candidates**: the Unity player log (`Player.log` / `output_log.txt`) in every Unity data folder `unityDataDirs()` names (see Handshake in `connection.md`), the macOS log roots, and `<gamePath>/Broforce_Data` — `playerLogPaths()` has the list, and awaits the Proton/WSL detection first; the UMM logs: the `Log.txt` beside each Doorstop target the user's game's processes name (below), `<profiles>/*/UMM/Core/Log.txt` under each of `r2modmanProfileRoots()` in `lib/steam-launch.js`, the roots the Steam launch looks profiles up in and in its order — `$XDG_CONFIG_HOME` when absolute, else `~/.config`, then the Flatpak r2modman's, then `%APPDATA%` and `~/AppData/Roaming`, each with `r2modmanPlus-local/Broforce/profiles` — on every platform (profile names are arbitrary — glob, never hardcode), and `Broforce_Data/Managed/UnityModManager/Log.txt` under the detected game path, beside UMM's own assembly, where it writes its log, which is found on Linux only, in any Steam library `findSteamGame()` searches. `Player-prev.log` is never a candidate
- **The player log is the log**: UMM's `Logger` writes each line to the console at once, which Unity copies into the player log, and to its own file only in batches every 0.5s of game time (never at time scale 0 short of 100 lines, never again once a write fails), while Unity's own output (uncaught exceptions, `Debug.Log*`) reaches the player log alone. The player log is truncated in place at a launch on Linux, so its `dev`+`ino` stays the same across runs
- **The game's own folders** (`gameDataLocations()` in `lib/game-process.js`, Linux, the user's game only): nothing for an instance or while `userGameOutOfReach()` names a reason, which it checks before it builds the proc reader, and neither derived nor remembered while `unplaceableInstancesReason('steam')` names one (registered from `index.js` through `setUnplaceableInstancesCheck()`, a throw counting as a reason), since every Broforce process, another session's instance included, then reads as the user's. For each owned process it reads the environment's config home (`XDG_CONFIG_HOME` when absolute, else `$HOME/.config`), Wine prefix (`WINEPREFIX` when absolute, else `$STEAM_COMPAT_DATA_PATH/pfx`) and Doorstop target, taking the union across processes. The target is the argument after `--doorstop-target-assembly` (Doorstop 4) or `--doorstop-target` (Doorstop 3) on the process's argv, split on NUL with a `Z:` path mapped to `/`, else `DOORSTOP_TARGET_ASSEMBLY` or `DOORSTOP_INVOKE_DLL_PATH` in its environment, else the flag on the argv of up to 8 ancestors up the `ppid` chain, since `run_umm.sh` turns the argument into the variable and execs the game. The last derivation that found anything is kept for the server's lifetime: while one finds nothing (the game gone, or a reader that throws) its folders, prefixes and UMM logs stand in as candidates, its UMM log never as the active one, and every list is ranked by mtime, so a fresher log elsewhere still wins. `forgetGameDataLocations()` is the tests' seam
- **The active UMM log** (`activeUmmLog()`): UMM writes `Log.txt` beside its own assembly, so it is the one beside the running game's Doorstop target, null when two owned games name different targets. Windows reads the `CommandLine` of Broforce's own processes from CIM (`Name` one of its images `AND CommandLine LIKE '%--doorstop-target%'`, `wmic` with the same `name=` clause when PowerShell cannot answer) and macOS `pgrep -lf '[d]oorstop-target'`, the pid and the arguments joined by single spaces, each taking the argument after the flag (`doorstopTargetsIn()`): a `"…"`-quoted one whole, an unquoted one up to the first `.dll` that ends a token, spaces included, since macOS's profile sits under `Application Support`. With no target, as for UMM installed into the game itself or no game, every UMM candidate stays in
- **Order**: `UNITY_INSPECTOR_LOG` is authoritative — a missing file there is the error, no fallback. Otherwise `preferredLog()`: the newest player log written since the game started, else the newest UMM log written since then — the active UMM log when there is one, else every UMM candidate. With no start time (game closed, detection unavailable) the newest player log wins unless a UMM log is more than 60s newer than it (`SAME_RUN_WINDOW_MS`), which only a run that wrote no player log produces. Nothing written since the start takes the most recently modified candidate
- **Staleness**: `gameStartTime()` in `lib/game-process.js` (null when unavailable) minus a 3s tolerance is the cutoff; a chosen file predating it carries `stale: true` and a `warning`
- **The instance target** skips all of the above discovery: the candidates are the instance's own `home/unity3d/Free Lives/Broforce/Player.log` and `profile/UMM/Core/Log.txt`, in that order of preference, with the same staleness rules, and `UNITY_INSPECTOR_LOG` does not apply — so neither the not-found error nor the stale warning advises setting it there: the not-found error names the instance's two paths and says they appear once its game has started, and the stale warning says neither has been written since the game started
- **A remote target** reads a local mirror of the game's player log and UMM log, synced through `execute_code` before each read, with no staleness; `UNITY_INSPECTOR_LOG` is ignored on a declared remote, and on the env path read locally with no mirror (`remote.md`)
- **`targetLogPaths()`** is what `game_state`'s `logs` and `run_test_script`'s snapshot both take: on an instance its two paths whether or not they exist; with `UNITY_INSPECTOR_LOG` the override as the player log when it is named `Player.log`, `Player-prev.log` or `output_log.txt`, else as the UMM log beside the newest player log; otherwise the UMM log `resolveLogFile()` chose or would fall back to, and the newest player log. While a start time is known, the player log is only ever one written since the game started, else null
- **`read_log`**: `lines` must be a whole number of at least 1, with `onlyNew` too. Without `onlyNew` the file is read backwards from its end in 64KB chunks (`linesBackward()`), and with `filter` streamed line by line keeping only the newest matches, so no read holds the file; the text is capped at 64KB, keeping the newest lines; a cut reply carries `truncated: true` and `droppedLines`, and a single line over the cap keeps its end
- **`read_log` with `onlyNew`**: calls run one at a time, and each target (the instance, `steam`, each remote endpoint) keeps its own position in `newLinesStates`. 64KB per call, cut forward to a line start, remainder flagged truncated; a line not yet ended by a newline is held back for the next call, and lines split on `\r?\n`. `filter` matches as without `onlyNew` (`lineFilter()`), and `lines` keeps the newest that many of the filtered new lines, blank ones counted as the plain tail counts them, the rest counted in `droppedLines` with `truncated: true` (`newLines` counts the non-blank lines returned); the position moves past every line the call read, filtered out or dropped. `isBaseline` is explicit on every read — `true`, with the last `lines` (20 by default) complete lines of the file's last 64KB, filtered, on the first call and whenever the file underneath changes, and `true` with no lines on `reset`. The position remembers the path, `dev`+`ino`, offset, the 256 bytes before the offset and the game's start time; a different start time (beyond the 3s tolerance) or bytes that no longer match mean the game rewrote the file in place, and rebaseline. While the game that started it still runs and still writes it, the read stays on its file even when `resolveLogFile()` would now choose another (`stickTo`)
