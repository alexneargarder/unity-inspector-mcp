# Log Files

`resolveLogFile()` in `index.js` picks the file for `read_log`; every response carries `path` and `modifiedAt`.

- **Candidates**: the Unity player log (`Player.log` / `output_log.txt`) in every Unity data folder `unityDataDirs()` names (see Handshake in `connection.md`), the macOS log roots, and `<gamePath>/Broforce_Data` — `playerLogPaths()` has the list, and awaits the Proton/WSL detection first; the UMM logs: `r2modmanPlus-local/Broforce/profiles/*/UMM/Core/Log.txt` under the r2modman config roots (profile names are arbitrary — glob, never hardcode), and `Broforce_Data/Managed/UnityModManager/Log.txt` under the detected game path, beside UMM's own assembly, where it writes its log, which is found on Linux only, in any Steam library `findSteamGame()` searches. `Player-prev.log` is never a candidate
- **The player log is the log**: UMM's `Logger` writes each line to the console at once, which Unity copies into the player log, and to its own file only in batches every 0.5s of game time (never at time scale 0 short of 100 lines, never again once a write fails), while Unity's own output (uncaught exceptions, `Debug.Log*`) reaches the player log alone. The player log is truncated in place at a launch on Linux, so its `dev`+`ino` stays the same across runs
- **Profile detection**: `detectActiveProfile()` looks for `profiles/<name>/` on the owned game's own command line, then in its environment (`run_umm.sh` passes the Doorstop target as `DOORSTOP_TARGET_ASSEMBLY`), then up the `ppid` chain — the wrapper consumes `--r2profile` and `run_umm.sh` consumes the Doorstop arguments, so the game's own argv usually carries neither. Two owned games resolving to different profiles is ambiguous and answers null, as a scan naming two profiles always has
- **Order**: `UNITY_INSPECTOR_LOG` is authoritative — a missing file there is the error, no fallback. Otherwise `preferredLog()`: the newest player log written since the game started, else the newest UMM log written since then — that profile's `Log.txt` when exactly one r2modman profile resolved, else every UMM candidate. With no start time (game closed, detection unavailable) the newest player log wins unless a UMM log is more than 60s newer than it (`SAME_RUN_WINDOW_MS`), which only a run that wrote no player log produces. Nothing written since the start takes the most recently modified candidate
- **Staleness**: `gameStartTime()` in `lib/game-process.js` (null when unavailable) minus a 3s tolerance is the cutoff; a chosen file predating it carries `stale: true` and a `warning`
- **The instance target** skips all of the above discovery: the candidates are the instance's own `home/unity3d/Free Lives/Broforce/Player.log` and `profile/UMM/Core/Log.txt`, in that order of preference, with the same staleness rules, and `UNITY_INSPECTOR_LOG` does not apply — so neither the not-found error nor the stale warning advises setting it there: the not-found error names the instance's two paths and says they appear once its game has started, and the stale warning says neither has been written since the game started
- **`targetLogPaths()`** is what `game_state`'s `logs` and `run_test_script`'s snapshot both take: on an instance its two paths whether or not they exist; with `UNITY_INSPECTOR_LOG` the override as the player log when it is named `Player.log`, `Player-prev.log` or `output_log.txt`, else as the UMM log beside the newest player log; otherwise the UMM log `resolveLogFile()` chose or would fall back to, and the newest player log. While a start time is known, the player log is only ever one written since the game started, else null
- **`read_log`** without `onlyNew`: `lines` must be a whole number of at least 1. The file is read backwards from its end in 64KB chunks (`linesBackward()`), and with `filter` streamed line by line keeping only the newest matches, so no read holds the file; the text is capped at 64KB, keeping the newest lines; a cut reply carries `truncated: true` and `droppedLines`, and a single line over the cap keeps its end
- **`read_log` with `onlyNew`**: calls run one at a time. 64KB per call, cut forward to a line start, remainder flagged truncated; a line not yet ended by a newline is held back for the next call, and lines split on `\r?\n`. `isBaseline` is explicit on every read — `true`, with the last 20 complete lines of the file's last 64KB, on the first call and whenever the file underneath changes, and `true` with no lines on `reset`. The position remembers the path, `dev`+`ino`, offset, the 256 bytes before the offset and the game's start time; a different start time (beyond the 3s tolerance) or bytes that no longer match mean the game rewrote the file in place, and rebaseline. While the game that started it still runs and still writes it, the read stays on its file even when `resolveLogFile()` would now choose another (`stickTo`)
