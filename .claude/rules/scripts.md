# C# Script System (Node.js side)

- `scripts/csharp/` holds source-controlled `.cs` files; `parseScriptMetadata()` reads `// #name`, `// #description`, `// #tags`, `// #args` headers
- `unload_script` sends the name `readScriptSource()` would load the given name under, so a catalog `#name`, a `.cs` name or an absolute path unloads that file's script; a name no file has goes as given. The mod's not-found error lists the loaded scripts
- **The mod runs each script command as one main-thread action**, so script work, `execute_code` and every Harmony patch a script makes are serialized by the main thread. A teardown — `Unload()`, the unpatch of each method the script's Harmony id patched, by that owner, and `DestroyImmediate` of its tracked GameObjects and of every scene component whose type its assembly declares — runs in one frame, and `unload_script` answers `destroyedObjects` and `destroyedComponents`. A `Main()` that threw or was stopped leaves the script loaded, and the reply says so with `loaded: true`. A script declaring a top-level type another loaded script declares is refused before it is registered. `Main()` and `Unload()` are the parameterless static methods of those names, for `compileOnly`'s `hasMain`/`hasUnload` as for a run
- `list_scripts` is Node-only. It and `scripts://csharp/catalog`, the same catalog as an MCP resource, list every script; the tool list carries none of it, since every session start would pay for it
- `execute_script` reads the file in Node and sends **source** over TCP, never a path to read — the game may run under Proton with a different filesystem. It also sends `origin`, the real path of the file `readScriptSource()` read (symlinks resolved, the filesystem's own case), which the mod compares, never opens: it refuses a different file under a loaded script's name. The name a script loads under is that real path's base name. A file that cannot be read is an error naming the path and whether it was taken as a library name or an absolute path. `args` that is not an object is refused before anything is sent. `args` values reach the script as strings, a non-string as its JSON text. With `compileOnly` it sends the mod's `compile_script`, whose reply is `types`, `hasMain` and `hasUnload`, or `compilerErrors` on a failure
- **Path safety**: absolute script paths are allowed; relative names must stay inside `scripts/csharp/`
- A relative name that matches no file is looked up as a catalog `// #name` in `readScriptSource()`, case-insensitively and exactly; several matches, or none, is an error naming the matches or the three closest catalog entries
- `list_test_scripts` / `run_test_script` cover `scripts/tests/`, the one directory holding every JSON test script; `list_test_scripts` and `list_scripts` list a file they could not read or parse under `errors`; an absolute path runs a script from anywhere. The tool answers with `compactTestScriptReply()` over `runTestScript()`'s reply: that reply is written whole to `resultsFile` in `testResultsDir()` — the session's own folder (`CLAUDE_SESSION_ID` when it is a valid id, else `pid-<wrapper pid>`) under `testResultsRoot()`, `$XDG_STATE_HOME/unity-inspector-mcp/test-results`, else `~/.local/state/...`, never `os.tmpdir()`, which nix-shell deletes when the server exits — pruned to that session's newest 100 on each write, which also clears every other session folder, and every results file left in the root, unwritten for 7 days; each step record shrinks to a 300-character `preview`, and the whole is shed level by level (passing previews, every preview, `logs`, the report's `events`/`stuck`/`survey` and other fields but `checks` over 2,000 characters, the whole `report`, the step lists), named in `omitted`, until it prints within 40,000 characters, since a larger MCP result is spilled to a file by the client. Steps dispatch straight to the game through `toolCommand()`, as the tools do, so `validateTestScriptSteps()` rejects Node-only tools as steps, a command that is no tool, whatever `toolCommand()` refuses, `execute_script` steps giving neither or both of `params.path` and `params.source` or `source` without `name`, a `wait` that is not a number from 0 to 2147483647 (`setTimeout` runs a longer one at once), a `params` key the step's tool does not declare (`execute_script` also takes `source`, `name` and `origin`, strings, which a `compileOnly` step's `compile_script` never receives), and a `params` value of a type the tool's schema does not allow, a null passing as absent, in the words `handleToolCall()` uses, in steps and cleanup steps alike once their placeholders are filled. A step key other than `command`, `params`, `wait`, `expect`, `until` and `report`, and in `prepareTestScript()` a script key other than `name`, `description`, `args`, `steps`, `cleanup` and `continueOnFailure`, is refused too, since a misspelt one would run the script without it. A `path` goes through `readScriptSource()` in `prepareTestScript()`, before anything runs, and the game is sent its source, with the file it read as `origin` on an `execute_script` step that names none; the step's record keeps the `path`
- A step's optional `expect` (`success`, `contains`, `notContains`) decides whether it passed: with `expect` a step failing as expected passes and the run continues, and any unmet expectation fails the step with the unmet list as its `error`. `contains` matches substrings of the step result pretty-printed, the way the tools return it, or of the error message when the command threw. An `expect` naming none of the three, or one whose `contains`/`notContains` is empty, is rejected by `validateTestScriptSteps()` — it would pass a step whose command failed
- **The rest of a script's shape**, all settled in `prepareTestScript()` before a command is sent, so a bad script runs nothing: `{{name}}` placeholders in step and cleanup `params`, nested included, are filled from the call's `args` over the script's declared `args` defaults (`{default, description}` each, which `list_test_scripts` shows) — a string that is only the placeholder takes the arg's JSON type, a placeholder with no value is a validation error naming it, and a given arg neither declared nor named by a placeholder is one too, since a misspelt arg would run the script on its default; `until: {timeout, interval}` (seconds, interval 1 by default, `expect` required) re-sends a step until its expect holds, sleeping `min(interval, time left)` so the last attempt lands at the deadline, stops early on a game-gone error, and records `attempts`, with `duration` covering every attempt; each attempt is an ordinary `sendCommand` under its own `commandTimeout()`; `report: true` lifts the step's `result` (execute_code's JSON string, or an object) into the reply's `report`, an array when several steps lift, and a result that is not a JSON object fails the step
- **Cleanup** runs after `steps` whatever ended them, unless the game is gone: the last step's thrown error with `isRunning()` answering false, or with it not answering true and the error being the client's crash or not-running message. A failed cleanup step never stops the rest; a game gone under one does, and `cleanupSkipped` says so. `passed` is every step and every cleanup step passed and no report's `passed` false. A script's `continueOnFailure: true` (boolean) records a failed step and runs on — a thrown one too, unless `gameGoneReason()` says the game is gone, which stops the steps and goes to cleanup — and adds `failures`, one `{step, command, error}` per failed step and cleanup step (`cleanup: true`), `error` being the first unmet expectation or the error's first line
- **`logs`**: `runTestScript()` snapshots `targetLogPaths()` and the game's start time after validation and attaches `collectLogDelta()`'s answer after cleanup on every path past it, failed steps and a dead game included. The player log is the one read, its console copies of UMM's lines included; the UMM log is read only when the player log gained nothing during the run or cannot be read, and only then, with the game not known to be gone, does the read wait `UMM_FLUSH_WAIT_MS` (600ms) for UMM's batch write. The reply carries `player`, and `umm` only when it was read. A log whose `dev`+`ino` changed, that shrank, whose 256 bytes before the snapshot's end no longer match, or whose game's start time changed is read from 0 and flagged `rotated`; one missing at the start is read whole; past 4MB a delta keeps its tail from a whole line and reports `skippedBytes`. `overlappingRun: true` marks a run another run on the same server overlapped, whose lines may be in either's delta. When the game is gone, `crashLog` carries the last 20 lines of the instance's `launch.log` that are not the launcher's own, the game's stdout, if it was written since the run started (`gameStdoutTail()`). Mod lines are attributed by their first `[...]` prefix, clipped to 80 characters, and never one of only digits and separators, a stamp or a number list, nor a bracketed line with nothing after it (`[Mod] [Script:x]` becomes `Mod › Script:x`, a `[Mod] Stack trace:` entry joins the one before it); in Player.log a prefixed entry continues only over frames and indented lines. Unity log calls come from Player.log's blocks ending `(Filename: ... Line: N)`: the trailer, the frames above it and the one line above them, since engine lines sit straight above a call, so a multi-line message keeps its last line, and the line above it too when the last is a bracketed detail such as `[Position out of bounds!]`; a call is credited as `origin` to the first frame's root namespace outside the runtime, Unity and Harmony — `Broforce` for the game's un-namespaced types; Player.log's other unprefixed lines are `Unity (engine)`, and Unity's native crash report (`Receiving unhandled NULL exception` on this game's Unity, then one `#N 0x... in fn` line per frame) is one error entry with its frames. Player.log's own `[Unity]` mirror lines are never counted, and a mirror's `red` or `yellow` colour sets the severity, `error` or `warning`, of the Unity call record below it. Messages group per source with stamps, frame counters, hex ids and digits normalized; a group of 50 or more is a flood, since a per-frame loop reaches that within a second while an ordinary line repeats a handful of times a run; only error, warning and flood groups are listed, with at most two variant samples; and the payload is shaped down level by level until it fits 12,000 characters (`truncated`, `omittedSources`, `omittedGroups`)
