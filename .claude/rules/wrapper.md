# Hot Reload (wrapper.js)

- `restart_server` stops the child, respawns it, and replays the MCP `initialize` handshake; one sent while a restart runs shares it and gets its answer, and one carrying any argument is refused, as every tool refuses an undeclared key. A start counts only once the new child has answered `initialize` and then the wrapper's own `tools/list` with a non-empty list, both within 10s, since a broken edit usually throws in the tool list rather than the handshake; the success message carries the count, and a failure names the error and the log. An unexpected child exit triggers the same sequence automatically, and restarts and respawns run one after another, never over each other; a start whose child fails stops that child and no other; the third death within 30s stops respawning and requests get a JSON-RPC error until `restart_server` clears the lockout. A request the wrapper cannot hand to a child while a restart or respawn is under way is told the server is restarting and to retry, since it never ran; one a child had when it crashed, or when a restart stopped it, is told the command may already have run in the game and to check the log or the game before retrying
- **With no child to answer them**, the wrapper answers `initialize` itself (the request's protocol version, `tools.listChanged`, the server's name and version) and `tools/list` with `restart_server` alone, so a server that dies at import still leaves the client a session in which `restart_server` works, and its `list_changed` brings the real tools; a respawn sends `list_changed` only once the client has initialized
- **Each child's stdout is decoded and buffered per child**, the client's stdin likewise as UTF-8, so a multi-byte character split across pipe reads survives. Outstanding requests are failed and the respawn decided on the child's `close`, not its `exit`, so its last answers are read first; `stopChild()` ends stdin, sends SIGTERM (on Windows, where `kill()` is abrupt, it first waits 2.5s for the stdin-end shutdown), waits 3s for `close`, then SIGKILLs. A response from a child for an id no longer outstanding for it — answered, failed, or cancelled by `notifications/cancelled`, which drops the id — is dropped and logged
- `UNITY_INSPECTOR_MCP_CHILD` / `UNITY_INSPECTOR_MCP_WRAPPER_LOG` let the tests drive the wrapper against a stub child
- **The wrapper's log** is `mcp-wrapper-<pid>.log` in `$XDG_STATE_HOME/unity-inspector-mcp/` (else `~/.local/state/unity-inspector-mcp/`), a 0700 directory, and in `os.tmpdir()` on Windows only, since nix-shell deletes its TMPDIR when its command exits; the file is 0600 and takes the child's stderr. Each start, never the reaper's, deletes this user's `mcp-wrapper-<pid>.log` and `.claim` files unwritten for 7 days in that directory and in `/tmp` off Windows, unless that pid is a live process, since a session can outrun the week and its claim, rewritten only with `owner.pid`, may be older than a week; a `.claim` goes only once its `.log` is unwritten for 7 days too, since an exited wrapper's reaper still reads the claim and the wrapper's hand-off line freshened the log. A log that cannot be opened leaves the child's stderr ignored, never the wrapper without a child. The client logs each command as its method, id, params byte count and the first 200 characters of its params
- **The wrapper's logger never throws** — a dead stderr, and a dead stdout, which only `sendToParent()` writes, are dropped silently rather than raised as errors, each noted once in the log file, so a shutdown that begins after the client took its pipes with it still runs to completion; twenty fatal reports within 5s exit the wrapper instead of a twenty-first
- **The wrapper stops the instance at session end**, since it is co-terminal with the session while the child is only what `restart_server` replaces. Every trigger — stdin end, SIGINT, SIGTERM, SIGHUP, and the fatal-burst exit — goes through one once-guarded `shutdown()`: when this session has an instance it first spawns a reaper, `wrapper.js --reap <job>` with `detached: true` and stdio ignored, so it has a session of its own that neither a terminal hangup of the group nor the client's SIGKILL reaches; then it stops the child (`stopChild()`) and exits. Clients do signal: Claude Code sends the wrapper SIGINT, SIGTERM 100ms later and SIGKILL 400ms after that, with no stdin close first, on exit and on a `/mcp` reconnect alike, and the MCP SDK client ends stdin and sends SIGTERM 2s later, so nothing the wrapper itself waits on survives the session end. The reaper is handed the wrapper's pid and start time, the child's, the trigger and its time, and takes the log and claim paths through the environment. It waits for the child to be gone — killing it 3s after the trigger if it is still the same process — so a launch the child had in flight is serialized ahead of the stop by the launcher's id lock and none can start after it. Only then does it read its claim file — the path the wrapper passed the child as `UNITY_INSPECTOR_MCP_CLAIM_FILE`, beside the wrapper's log unless that setting names one and written mode 0600 by the server, holding the one line the server wrote there: the absolute `owner.pid` path — and then that `owner.pid`: no claim file, no owner file, an unreadable one (logged with the error's code) or one naming another pid, and it leaves. Naming the wrapper's pid and start time, it polls the file every 500ms until `UNITY_INSPECTOR_MCP_STOP_WAIT_MS` (default 15s) after the trigger, so a server reconnecting on `/mcp` takes the id over, and if it still names the wrapper it `spawnSync`s `instanceConfig()`'s own `instance <id> stop` command with stdio ignored under `INSTANCE_STOP_TIMEOUT_MS` (60s), logging how that command ended — a spawn that failed, a non-zero status or a signal, or a clean stop. It never removes `owner.pid`; it deletes the claim file as it exits, and the wrapper deletes it itself only when it spawned no reaper. `restart_server` never reaches any of this. Every elapsed-time log line names its trigger — `after stdin end`, `after SIGINT`, `after SIGTERM`, `after SIGHUP` — the hand-off, the stop and the wrapper's own exit line alike, so a real session end shows what grace period there was. The wrapper imports `lib/instance.js` and nothing else from `lib/`, and takes only the id, the stop command and its budget from it; `lib/instance.js` imports only `path` and `lib/command-line.js`, which is what keeps that true
- The reaper paths are tested against both clients' real sequences: `claudeCodeClose()` and `sdkClientClose()` in `test/support/wrapper-harness.js`, `startWrapper(env, { detached: true })` for a group hangup, and `waitForReaper()` for the detached process's end
- **id=0 gotcha**: MCP uses `id: 0` for init — check ids with `!== undefined && !== null`, never truthiness
