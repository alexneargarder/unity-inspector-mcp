# Instances

- **Which instance**: `CLAUDE_SESSION_ID` names it. A session has an instance when the platform is Linux, the id matches `^[A-Za-z0-9_-]{1,64}$`, `BROFORCE_INSTANCE_CMD` names a launcher, and that launcher's `--help` names `instance <id>`; a malformed id is logged to stderr once and treated as absent, never thrown. Anything else means no instance and the server serves the user's game as it always has — never a refusal. `lib/instance.js` derives the id and the launcher commands; `withRoot()` turns that into `<root>/<id>/` and from it `profile/UMM/Core/Log.txt`, `home/unity3d/Free Lives/Broforce/` (`unityDataDir`, the game's Unity data folder) and its `Player.log`, `work/`, `game.pid`, `port`, `launch.log`, `owner.pid`, and the commands `<launcher> instance <id> launch|stop|remove` and `<launcher> instance list --json`, whose output is **JSON Lines** — a header object (the first with no `id`) carrying `instancesRoot` — the directory holding one directory per instance, and the only place the server learns it — `stageRoot` where the launcher reports one, and `cap` from a launcher that caps running instances (absent or null from one that does not, both read as no cap); the header's own `root` is the launcher's game root and is never read, then one object per instance directory (`id`, `running`, `pid`, `port`, `display`, `last_launch`, `stale`), which `summarizeInstanceList()` parses line by line, skipping any line that does not parse. The port is never derived and `--port` is never passed: the launcher allocates it and the server reads `port` back. **The launcher rewrites `port` on every launch, before `game.pid`** — a hard requirement of the contract, since the server accepts the file only when its mtime is at or after the spawn it is waiting on
- **Target**: the server holds one explicit target, `instance` or `steam`, in `index.js`. `resolveTarget()` settles it once — `instance` when the session has one, the probe passed and the root is known (`instanceTargetReady()`), else `steam` — and adopts a running instance as it does, so a server started beside one serves it without being told; only `launch_game` changes it after that (`steam: true` for the user's game, nothing for the instance). **Only an answer settles it**: while the session has an instance id and a usable launcher whose `--help` went unanswered or whose list gave no root (`targetPendingReason()`), the resolution is left open (`targetPending`, `resolveTarget()` answering null), every tool but `game_state`, `launch_game` and the target-free `list_scripts` and `list_test_scripts` is refused with that reason by the gate in `handleToolCall()` — nothing reaches the user's game — and `game_state` reports `target: null` and the reason; the next call past the launcher's cooldown resolves again, claims and adopts. A resolution under way when an explicit switch lands (`targetGeneration`) leaves the switch alone. **A tool call keeps its target**: every call but `launch_game`, `stop_game` and the target-free ones is counted in `boundCalls` from its first moment, and `launch_game` refuses a switch while any is running, checked again with nothing awaited before `setTarget()`; `launch_game` counts itself from just before its own switch, so a second launch cannot switch back inside that switch's await. **A launch validates everything before it switches** — the unplaceable-instances refusal, `launchArgs`, the launch command, the restart pre-flight — and a first spawn that fails puts the previous target back (`restoreTarget()`). `activeConfig()` is what every detection, kill, log and launch call takes; `unityClient.pointAt({port, gameConfig, noPortMessage})` re-points the client and disconnects on a switch, `gameConfig` is what the crash detector inside `sendCommand` watches, and `noPortMessage` is what the connect stage says when the target has no port — `noPortMessage()` names the instance, so every tool fails with the same reason `pollUntilResponsive` gives. `launch_game` and `wait_for_game` are refused while a command is in flight or queued, or a `simulate_input` plan is between its polls, since both may drop the socket under it and it would be answered from whatever answers next. **The recorded `port` is used only while a game of ours is running** — `instanceOwnsGame()` (an owned process in the scan, or a validated pidfile), re-checked on every `pointClientAtTarget()`, since the launcher hands a freed port to whichever instance asks next and a stale number would run this session's commands inside somebody else's game; with no owned game the client has no port and commands say so
- **The launcher probe**: `--help` is the only question safe to put to a launcher that may have no instance mode — one without it takes any other first word for a profile name and launches the user's game. The verdict is the phrase `instance <id>` anywhere in its output of an exit-0 `--help`, so the program's own name is not part of the contract; the setting's leading arguments go to `--help` as to every other verb (`leadingArgs`). It runs once per process, started eagerly at startup so the MCP handshake does not wait on it, and commands await its verdict — but **only an answer settles it**: a `--help` that could not spawn, timed out or exited non-zero leaves `instanceModeChecked()` null and is asked again after the same 15s cooldown the root discovery has (`launchTiming.probeRetryMs`, and `forgetCommandHelp()` drops the memoized capture so the retry really runs it), while a `--help` that ran cleanly and does not name the phrase is final for the process — asking that launcher again would only hand `instance` to a program that reads it as a profile name. How the last unanswered `--help` ended (`instanceProbeFailure()`: could not be run, with the spawn error; did not finish within 5s; or the exit status and the first line it printed) is appended to every reason that names it, so a typo or a PATH problem shows through. `restart_server` re-asks everything by being a new process. The `--help` run itself is `captureCommandHelp()` in `lib/game-process.js`, 5s and memoized per command line, so a program named in both `BROFORCE_INSTANCE_CMD` and `BROFORCE_LAUNCH_CMD` is asked once and its answer serves the probe and the argument channel alike; `resetInstanceModeProbe()` clears both memos for the tests
- **The instances root**: the launcher owns it and this repository hardcodes none. `discoverInstancesRoot()` in `index.js` runs `<launcher> instance list --json` once, after the probe has passed and never before — `instance` must not be handed to a launcher that has no instance mode — and reads `instancesRoot` from the header, plus `stageRoot` where the launcher reports one, both resolved through symlinks (`canonicalPath()`, which keeps a not-yet-created tail as given), since `/proc/<pid>/cwd` always reads the resolved path — the two roots `withRoot()` hangs `stagePath` and every instance path off; a header naming no `stageRoot`, or one that is not absolute, leaves the session with no stage at all, the non-absolute one dropped to null exactly as a non-absolute `instancesRoot` is. `withRoot()` then rebuilds both memoized configs, the instance's and the user's game's, so every path and the cwd rule alike come from that one answer. **Both the probe and the discovery run whenever `BROFORCE_INSTANCE_CMD` is set**, whatever `CLAUDE_SESSION_ID` says (`sessionLauncher()` is the launcher without an instance, `launcherRootKnown()` the two questions), since the instances root is also what keeps another session's game out of this server's `stop_game`; with no launcher configured the root is unknowable and every Broforce process counts as the user's, which the README says. Both run **on Linux only** (`setServerPlatform()` injects the platform for the tests), since instances are a Linux arrangement and off it nothing about the launch is this server's business. The list gets its own 4s budget and the probe's `--help` 5s, so the two together settle well inside the 15s takeover poll a replaced server's reaper is sitting in. **A failure is remembered for 15s, not for the process's life** (`launchTiming.rootRetryMs`): the next caller past the cooldown asks again, since until the launcher answers the user's game cannot be told from another session's instance. A discovered root is `Object.assign`ed into the memoized configs rather than replacing them, so a config handed out before it was known — the client's `gameConfig`, a caller's local — gains it too; `stop_game` and `launch_game`'s restart still ask for the refusal before taking the config, since that call is what triggers the retry. A list that cannot be read, or one whose header names no absolute `instancesRoot`, means no instance yet: it is logged, a session with an instance id has no target until it is answered (see Target), a session without one serves the user's game under the unplaceable-instances guard, and the reason reaches `game_state`'s `instanceReason` and `launch_game`'s reply alike. `instanceTargetReady()` is those two questions plus a session id of this server's own, and both `resolveTarget()` and `launch_game` go through it, since `setTarget()` can settle the target without any of them

- **Ownership**: a Broforce process is one whose `/proc/<pid>/comm` is `Broforce.x86_64`; one whose comm starts with `Broforce` and whose `argv[0]` basename matches `/^Broforce.*\.x86_64$/`, which is how a renamed copy of the binary with a bare argv is found; or one whose command line names `Broforce*.exe` and whose comm is a wine/proton form or a `Broforce`-prefixed name. `comm` truncates at 15 characters, so `Broforce_beta.exe` arrives as `Broforce_beta.e`. The Proton half of that rule is command-line only and has not been exercised against a live Proton launch. An instance owns the one whose `/proc/<pid>/cwd` is its `work/`; the user's game is any whose cwd is *not* under the instances root, and with no launcher to report that root, any at all. Every detection, start time and kill obeys this, so the two never see or stop each other
- **Launch on an instance**: a `restart` that could not stop the game (`unknown`, or survivors) launches nothing and reports the survivors. Whether a game is already running is the cwd rule's answer, never a ping — a ping answered on a recycled port is somebody else's game and must not refuse the launch. Preconditions first — a validated pidfile naming a live game refuses the launch (a listener on the instance's port does not, since the launcher reallocates a port whose listener is not this instance's game). Then the launch command is run and *waited out*, since only its exit carries the verdict and its port is written before it finishes. **This server's own launch and stop of the instance are serialized** (`acquireInstanceOp()`): `stop_game` on the instance waits for a launch in progress to get its launch command's verdict — the command and any cap wait — before it reads what is running and asks the launcher, so a stop never runs blind behind it; the launch's poll then finds the game gone. Exit 75 is a capping launcher's refusal at its cap: the server polls `<launcher> instance list --json` every 5s for up to 120s (its own budget, not the launch budget), relaunches on a free slot with a fresh 180s budget, and on expiry words four endings apart: a last readable list that was full (its ids are the slot holders), a last readable list the refusal disagreed with (reported as what the list showed, never as holders), a list unreadable on every attempt, and a budget spent before the list was ever checked; a readable list is kept as `runningInstances`. The last readable summary is carried across polls and across re-entries — one failed poll is one poll, and the wait that happens to end the loop says nothing about the polls before it. An unreadable list still counts as a freed slot and the launch is retried, as does a list reporting no cap — a launcher that caps nothing never holds a launch up — while a cap of 0 frees nothing and is reported at once as allowing no instances. A list line that does not parse is counted in the summary's `unparsed` and named in the cap message, since the instance it described is missing from the count. Any other non-zero exit is reported at once with the `launch.log` tail, or with the tail of the launcher's own stderr when there is no log yet — a launcher refusing a brand-new id has created nothing to write to. After a clean exit — and unless the launch was `vanilla`, which has no port and no inspector to wait for — the server waits up to 10s for a `port` file **written by this launch** — one whose mtime predates the spawn is an earlier run's allocation, which may since have gone to another instance — re-points the client and polls until the game answers. That freshly allocated port stands in during that launch's own poll only, and only until 180s after the `port` file's mtime (`launchedPortUntil`, `launchTiming.portReservationMs`), the contract's reservation of a recorded port; from the next command on the ownership gate applies as usual. A `port` that never appears is a `no-port` failure, worded differently for a launcher that had not finished and for a file the launch did not write, which the message dates. The failure tail is this launch's too: a `launch.log` older than the spawn is an earlier run's and gives way to the launcher's stderr. A polled launch's reply carries `instance: {id, port}`, the two log paths and `runningInstances`; a `vanilla` one has no port to report. A launch that finds the instance already running carries the same `instance` and `logs` fields, since the game it would have started is the one already there
- **Unplaceable instances**: while a launcher is configured and this server cannot place its instances — the `--help` went unanswered, or the mode is there and the root is not — every Broforce process reads as the user's, and `unplaceableInstancesReason()` in `index.js` is the one cause with two consequences. `steamKillRefusal()` wraps it for the kill: `killGame`'s `signalRefusal` returns `unknown: true` without signalling, so `stop_game` is a failure naming the reason. `launch_game` on the `steam` target asks the cause directly, before it decides whether a game is already running — a stranger's would read as the user's, broken — and answers `state: "root-unknown"` having launched and stopped nothing, `restart` included. Asking is also what drives both retries. `BROFORCE_STOP_CMD` still runs first when it is set, since it is the user's own tool and knows its own game; only the signal is this server's guess. Only a clean `--help` verdict of "no instance mode" lifts it, since that launcher runs no instances; with no launcher configured, or off Linux, there is nothing to protect and the kill runs as it always has. `instanceField()` awaits `launcherRootKnown()` before it reports anything, whatever this session's id says, so `game_state` drives both retries — for a session with no instance of its own too — and its `instanceReason` tells an unanswered `--help` from a launcher that answered and has no instance mode
- **Stop**: `stop_game` acts on the target only. With no game running, the user's game is left alone and no launcher is called — the reply says nothing was signalled — while an instance still goes through the launcher's stop — it tears the display down and clears the pidfile — and the reply says it tidied the instance up, answering `success: true` when that stop ran and exited 0, since the tidy-up is what the call asked for, and `false` when it could not run or exited non-zero. An instance is stopped with `<launcher> instance <id> stop` under `INSTANCE_STOP_TIMEOUT_MS` (60s, in `lib/instance.js`, the contract's budget, a wait on an in-flight operation of the id included), since that also tears its display down; a command past its budget is reported as not having finished within it (`commandFailure()`), never as one that could not run; a process still alive afterwards falls back to signalling, while a non-zero exit that left nothing running is still a stop and carries the exit status as a note — the targets are re-derived from a fresh `/proc` scan first — and the answer says which path stopped it. A running user's game goes through `BROFORCE_STOP_CMD` first (`userStopCommand()`, tokenized like every other command setting, the same 60s budget as the instance stop), verified by the ownership rule afterwards; a non-zero exit, a command that could not run, or a process still alive afterwards falls back to the same pid-scoped kill and says so, while a non-zero exit that left nothing running is still a stop with the exit status noted, and `launch_game { restart: true }` takes that same path. With the setting unset the pid-scoped kill is the whole of it. `BROFORCE_STOP_CMD` is a user's-game setting and is never consulted on the instance target. `remove: true` then runs `<launcher> instance <id> remove`, under the same budget; it is refused while the target is `steam`, and skipped with `removed: false` and the reason whenever the stop answered `unknown` or left survivors — `killGame` reports the pids that outlived it as `survivors`, since a stop that killed one of two processes is not a stop and deleting the directory would orphan the rest
- **The help channel**: `launchArgumentHelp()` renders `launch_game`'s description tail on every listing from two captures: `startLaunchHelpCapture()` of `BROFORCE_LAUNCH_CMD`, and `startInstanceHelpCapture()` of the instance launcher, taken only while `instanceTargetReady()` says a plain call runs the instance launch (own session id, instance mode, known root). Each runs `--help`, and `--args-help` only when that exited 0 and names it: an unknown flag might launch an unknown launcher's game. `argsHelpRecord()` memoizes per command line. A `--help` that could not answer is dropped with its `captureCommandHelp()` memo and re-asked by the next listing; a clean answer without the flag is cached for the process. Only the first listing waits, up to `ARGS_HELP_GRACE_MS` (1500ms), for readiness and the captures; later listings never wait. Until readiness first settles the tail only says help will follow; during a re-ask the last settled answer stands. `scheduleTailFollowUp()` re-renders when outstanding answers land and, if the tail changed, sends `notifications/tools/list_changed` (`listChanged: true` in capabilities, forwarded by `wrapper.js`): once per change, never before the first listing or while answers are outstanding, never thrown. `setToolListChangedNotifier()` is the test seam. One program in both settings with unlabelled output is one block; otherwise each launch has a section, instance first: a verbatim fenced block, a "publishes no argument help" line, or, with no launch command, `steamArgumentHelp()`'s line: on macOS the Steam protocol launch's no-arguments line, elsewhere that `launchArgs` follow `-applaunch`'s Doorstop arguments and the protocol fallback takes none. `parseArgsHelp()` splits labelled output into per-launch sections by the contract's header rules. Each block is capped at 1KB in bytes, so the tail adds at most 2KB; `test/tool-list.test.js` measures the tool's own text, `test/launch-help.test.js` pins the worst-case tail
- **`owner.pid`**: `<root>/<id>/owner.pid` holds one line, `<pid> <starttime>` — the wrapper's pid as `process.ppid` read at startup (`WRAPPER_PID`) and field 22 of its `/proc/<pid>/stat`, read once and memoized by `ownerIdentity()`, both decimal — and records only that this wrapper owns the id, never that a launch succeeded. `writeOwnerFile()` refuses once `process.ppid` is no longer that pid: a server that outlived its wrapper is reparented, and a claim naming init or a subreaper would keep the launcher from ever reaping the game. During `shutdownServer()`'s grace it writes anyway, naming that recorded identity, since the client kills the wrapper within it and the wrapper's reaper, which compares the file against that identity, still runs the stop. The file is written to `owner.pid.<pid>.tmp` beside it and renamed over it, so a concurrent `claimInstance()` never reads a half-written line as malformed. **Every claim goes through `claimInstance()`**, which writes over a claim only when it is malformed, names a dead wrapper (the pid's `/proc` start time no longer matches), or names an older live wrapper of the session: during a `/mcp` replacement the old server can still be running, and polling, beside the new one until its wrapper's shutdown has stopped it, and the newer wrapper's claim must win that overlap. `resolveTarget()` claims whenever the instance directory exists, game or none; with no directory yet it sets `startupClaimPending`, and the first `pointClientAtTarget()` after the directory appears claims it. After that `pointClientAtTarget()` and `launch_game`'s already-running reply claim whenever a game of the instance is running, so a game another server's launch finished, or one that came up after startup, is still stopped at session end. A launch claims it before an instance launch command is spawned when the instance directory is already there, and otherwise as soon as the launcher has created it during that launch — `claimInstanceWhenCreated()` looks every 100ms for as long as the launch command runs, whatever the launch then ends as, and gives up when it ends with nothing there. A shutdown (`shutdownServer()`, on any of its triggers) arriving while that watch runs keeps watching within its 2s grace, beside any sweep teardown, so a directory created in that window is claimed before the server exits, the wrapper already killed included. The claim never creates the directory: the launcher creates a missing instance on its first launch, and a directory holding nothing but `owner.pid` reads to it as one that already exists. It is written at startup too, where `resolveTarget()` claims as soon as the root is known and before the client is pointed — the probe and the list that answer it take milliseconds, well inside the 15s the old wrapper's reaper waits — so a server reconnecting on `/mcp` wins the id before that wait runs out; `adoptRunningInstance()` then points the client at it. Every write also records the `owner.pid` path in `UNITY_INSPECTOR_MCP_CLAIM_FILE` when the wrapper named one, since the wrapper derives no root of its own. `stop_game` removes both once the stop left no survivors; the wrapper never does
- A stop by signal leaves the display the launcher created for the instance up; that is harmless and the next launch reuses it
- That fallback, and every stop of the user's game, prefers the validated `game.pid` — the pid's cwd must still match, and a pidfile that fails validation is deleted — and falls back to the scan. The pidfile is removed only once every target is gone, so a kill that failed leaves it in place. Nothing on Linux is ever killed by name
- A launch waits 180s, since setting an instance up (window, audio, port) outlasts a Steam launch. Failures carry the last 20 timestamped `launch.log` lines, read from the file's last 64KB only (`readFileTail()`) — the game's stdout lands in the same file, so it can be any size and untimestamped lines are dropped
- **The session's stage**: `game_state`'s `instance.stage` is the session's own `stagePath`, `<stageRoot>/<id>/UMM` off the stage root the launcher's list header reported — where this session builds, whatever the running game was composed from — and null from a launcher reporting no stage root
- `read_log` on an instance uses the two derived log paths and skips r2modman profile discovery entirely; `game_state` names them on every reply, alongside `target`, `port` (the target's own: 9999 or `UNITY_INSPECTOR_PORT` on `steam`, the instance's while a game of ours runs there, else null), `instance` (its `port` by the same rule, whatever the target), `runningInstances` (the launcher's list through `sessionLauncher()` whenever the root is known, on either target), and `build`
- **`build`** on `game_state`: `gameBuild()` in `lib/game-process.js` finds the target's running game's directory — `/proc/<pid>/exe` of an exact or renamed binary, else the Proton command line's `Broforce*.exe` with its `Z:` drive mapped to `/`, and on Windows CIM's `ExecutablePath` — and `storeOfGameDir()` names its store from what each store leaves: `goggame-<id>.info` in the directory (`gog`, its `buildId` as `storeBuild`), or a `steamapps/common/<dir>` path whose `steamapps/appmanifest_274190.acf` carries `buildid` (`steam`). `version` and `buildDate` are the game's own `VersionNumber.version` and `versionDateString`, asked once per connection through one `execute_code` (15s budget) and memoized per socket, since store build ids are not comparable across stores. A test leaning on one store's behaviour checks `build.store` with `game_state` before its run, or an `execute_code` step reading `Application.dataPath`. macOS reports no directory, and `build` is null with no game running
- Windows and macOS keep the name-based behaviour; instances are a Linux arrangement, and switching target leaves the other target's game running, which the launch reply says when that game is still up
- **No launcher is named anywhere in this repository**, CLAUDE.md included: the launcher is a setting, and `docs/launcher-contract.md` is what someone writing one implements
