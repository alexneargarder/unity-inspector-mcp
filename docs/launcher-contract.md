# Instance launcher contract

The contract a launcher named in `BROFORCE_INSTANCE_CMD` implements.

`BROFORCE_INSTANCE_CMD` holds a command plus optional leading arguments, parsed with shell-style quoting, and the server appends a verb to it, so the program name doesn't matter.

## What the server needs

A launcher that does these and nothing else works with the server.

- **`--help`**: exits 0 within 5 seconds and prints usage naming `instance <id>`. Help that doesn't name it means the launcher has no instance mode.
- **`instance <id> launch`**: creates the instance if it isn't there yet and starts its game. Exit 0 once the game is started, and any non-zero exit means it refused or failed. Exit 75 is the one exception, and only from a launcher that caps how many instances run at once. It means the launcher is at that cap, and the server waits for a slot and launches again. `<id>` is the session id and matches `^[A-Za-z0-9_-]{1,64}$`.
- **`instance <id> stop`**: stops that instance's game and takes down the display it created. **`instance <id> remove`**: deletes the instance directory and leaves that instance's own lock file under the instances root. Each finishes within 60 seconds, a wait on a launch or stop of the same id already in flight included: a stop arriving during that id's launch ends the launch, or waits for it, inside that budget, and then stops whatever it started; the launch it ended exits non-zero with its reason in `launch.log`, which the server quotes. A launch still waiting for the id's lock when a stop or remove overtakes it starts nothing and exits non-zero, printing the reason to stderr, which the server quotes. A stop that cannot take the id's lock inside that budget stops nothing: it exits non-zero, printing to stderr what holds the lock and that nothing was stopped. `stop_game` quotes that line and signals a game still running, and the session-end stop logs the exit and leaves the game for a later launch to find unowned. Past 60 seconds the server kills the command and reports it as not finished. Both are judged by their exit, so neither may leave a background process holding the stdout or stderr it was given.
- **`instance list --json`**: JSON Lines, within 4 seconds. A header object first, then one object per instance with `id`, `running`, `pid`, `port`, `display`, `last_launch` and `stale`. The header is printed even when there are no instances yet. Every line is a complete JSON object, every string in it escaped as JSON requires, control characters included: a line that doesn't parse drops its instance from the count the cap wait reads. Header fields:
  - **`instancesRoot`**: absolute path of the directory holding one directory per instance. Required, and every instance path comes from it. A header without it means no instances. The server resolves symlinks in it, since a game's working directory always reads as the resolved path.
  - **`cap`**: how many instances this launcher runs at once, a non-negative integer. A launcher that caps nothing leaves it out or reports it null, which reads as a slot always being free. A cap of 0 runs none, and a launch refused at it is reported at once.
  - **`stageRoot`**: optional, an absolute path. The stage root: `<stageRoot>/<id>/UMM/` is where this session builds, and `game_state` reports it as `instance.stage`, whatever the running game was composed from. A launcher that leaves it out gives the session no stage.
  - No other header field is read, `root` included.
- **Instance directory**: `<instancesRoot>/<id>/` holds `profile/` (the mod profile, log at `profile/UMM/Core/Log.txt`), `home/` (the game's config home, log at `home/unity3d/Free Lives/Broforce/Player.log`, beside the `unity-inspector-<port>.token` the mod writes, which the server reads there), `work/`, `port`, `game.pid`, `owner.pid` and `launch.log`.
- **`port`**: the inspector port the launcher allocated, the lowest free port in 9900-9998. The port your own game listens on (9999, or whatever `UNITY_INSPECTOR_PORT` names) is never handed to an instance. It gets rewritten on every launch, before `game.pid` is written, and the server never picks one itself. A port a launch recorded isn't handed to another instance for at least 180 seconds after it was written to `port`: until it can recognise the game as the instance's, the server polls the game on that port for as long as that holds, counted from the file's modification time. The instance's game has to listen on that port: the launcher patches it into `profile/UMM/Config/Unity Inspector Mod/Settings.xml` after it has composed the profile, writing a file holding only `serverPort` when the composition left none there.
- **Working directory**: the game process runs in the instance's `work/`. The server uses that to tell one instance's game from another's and from your own.
- **`owner.pid`**: written by the server. A launcher may read it to tell an owned instance from an abandoned one but never writes it, deletes it only with the instance directory, and never stops on its own an instance whose `owner.pid` names a live process; `instance <id> stop` and `remove` act whatever it says. One line, `<pid> <starttime>`: the pid of the MCP wrapper that owns the id, and field 22 of that pid's `/proc/<pid>/stat` (clock ticks since boot), both decimal. The server replaces it whole, renaming a temporary file beside it over it, so it is never read half written. At the end of its session the wrapper hands the stop to a process of its own that outlives it, which runs `instance <id> stop` 15 s later if the file still names the wrapper. Two wrappers of one session overlap while a client reconnects, and the claim goes to the newer: a server writes over a claim only when it is malformed, names a process that is gone, or names an older wrapper still running. Writing it never creates the instance directory, so a launcher creating a brand-new instance finds nothing there ahead of it.
- **`--vanilla`**: launch without mods, appended to `instance <id> launch` and to `BROFORCE_LAUNCH_CMD` alike. It is the one flag the server ever adds on its own, and the one spelling it recognises when a caller passes it in `launchArgs` before any `--`, which moves it ahead of the rest of them: a short alias the launcher also accepts is launched, but polled as a modded launch.
- **`--args-help`** (optional): prints the launch arguments the program accepts, within 10 seconds. The server runs it only when `--help` lists it, and quotes what it prints to callers for every launch it runs through the program: your own game launch and `instance <id> launch`, which take different arguments. Label them so each caller reads its own. A label is a header alone on its line at column 0, `[instance launch]` or `[plain launch]`, and its block runs to the line before the next header; print nothing before the first header. A block under any other header is dropped, a header printed a second time adds nothing to the block already read under it, a launch with no block of its own is reported as publishing no argument help, and output with no header at all is quoted for every launch. At most 1 KB of each block is quoted, cut on a character boundary and marked where it was cut, so keep each one short.

## What isolation adds

The server reads none of these and behaves the same with a launcher that does none of them; they are what the build workflow relies on when a session builds into a private copy.

- **Composing the profile**: every launch rebuilds `profile/UMM/` before it starts the game, from the launcher's source profile, which is the mod profile it starts your own game from by default. `Mods/`, `BroMaker_Storage/`, `Core/` and `Config/` are copied with deletion, so a mod you took out of your profile leaves the instance too, the files the copy leaves out included: a directory the source no longer has is removed whole, and so is a copied `Mods/` directory carrying the UMM mod `Id` of a directory the stage overlaid, since UMM loads one directory per `Id`, whatever their names. The same exclusions apply when the instance is first created, so nothing left out of the copy ever reaches it from the source. Left out of the copy: `Config/Unity Inspector Mod/` and `Core/Log.txt`, only at the root of `Config/` and `Core/`; `*.log` files at any depth in `Mods/`, `BroMaker_Storage/`, `Config/` and `Core/`; and `Screenshots/` and `Results/` directories at any depth in `Mods/`, `BroMaker_Storage/` and `Config/`, which keeps a mod's own runtime output out of instances.
- **The stage overlay**: when `<stageRoot>/<id>/UMM/` is there, each top-level directory under its `Mods/`, `BroMaker_Storage/` and `Config/` replaces the instance's copy of that name, or is added when there isn't one. Every `Mods/` entry overlaid from the stage whose `Info.json` carries an `Id` is enabled in `Params.xml`, with the entry added when the mod has none there; one without an `Id` is overlaid and left as UMM finds it. A session builds into its stage and the launcher only reads it.
- **The composed receipt**: every launch, right after composition and before the port patch and `game.pid`, the launcher writes `<instancesRoot>/<id>/composed` as JSON Lines, replacing the previous one. A header `{"composed":<epoch seconds>,"stage":<the composed stage's UMM path, or null when no stage was composed>}`, then one line per composed mod directory: every directory in the instance's `Mods/` and `BroMaker_Storage/`, plus each `Config/` directory the stage overlaid, as `{"kind":"Mods"|"BroMaker_Storage"|"Config","name","source":"default"|"stage","path","buildId","builtAt"}`. `path` is the source directory the entry was composed from, never the instance copy. `buildId` and `builtAt` are the string values of that name in the source's `.build-stamp.json`, each null when the source has no stamp or the stamp has no string value for it, and always null for a `Config` entry. A receipt that can't be written refuses the launch.
- **Locks**: composition holds the source profile's `UMM/.install.lock` while it copies and the stage's `.install.lock` while it overlays, waiting up to 120 seconds for each. A wait that runs out refuses the launch and names the lock it couldn't take in `launch.log`.
- **Saves**: at instance creation the launcher seeds `work/Saves/progress.sav` from your own save, that file and no other. It goes in once and is never copied back, so progress in either game stays separate. `Options.xml` stays the game's default.
- **After the launch**: the launcher may set the instance's game up once its inspector answers, connecting with the token from `home/`: a cap on the frame rate, a muted audio stream. That is a second inspector connection, and a main-thread action, during the server's first commands, and a frame-rate cap makes the instance run at a different rate from your own game, so a launcher doing it logs the rate it applied in `launch.log`. A launcher that talks to the inspector after a launch opens every connection with the hello, `{"id":"hello","method":"hello","params":{"token":"<token>","protocol":<n>}}`, reading the token from `unity-inspector-<port>.token` in the game's Unity data folder once the connection has completed. The mod refuses a hello naming another protocol: it answers `success: false` with its own number as a top-level `protocol` beside the `error`, and closes the connection. On that refusal the launcher retries once, on a new connection, with that number. A refusal with no `protocol`, or a refused retry, is final.
- **Disk**: an instance's game runs with core dumps off, since a crash would otherwise leave a core the size of the game's memory in `work/` until the instance is retired.
- **On launch**: the launcher stops the game of an instance that nothing owns any more: its `owner.pid` is absent or names a process that is gone, and the launcher's own record of the session that launched it shows that session gone. It skips any instance with a launch or a stop of its own in flight, and never stops on its own one whose `owner.pid` names a live process. It removes a stage directory once no instance directory for that id is left and nothing under it has been written for the launcher's idle-instance retirement period. Retiring idle instance directories at all, and after how long, is the launcher's own policy; the stage rule only follows it.
