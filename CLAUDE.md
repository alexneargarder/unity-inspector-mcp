# Unity Inspector MCP Server

Node.js MCP server bridging Claude to the Unity Inspector Mod running inside Broforce.

**Test**: `nix-shell -p nodejs_22 --run "npm test"` — `npm test` runs `node --test test/*.test.js`, naming only the test files, so shared stubs live in `test/support/` without ever being run as tests themselves. Every test file imports `test/support/session.js` first, before `index.js` or anything under `lib/`: it deletes `CLAUDE_SESSION_ID`, `BROFORCE_INSTANCE_CMD`, `BROFORCE_STOP_CMD`, `STUB_STAGE_ROOT`, `UNITY_INSPECTOR_MCP_CLAIM_FILE` and `XDG_CONFIG_HOME` (a test that wants the last sets a temp value of its own) and points `BROFORCE_LAUNCH_CMD` at a no-op command, `UNITY_INSPECTOR_TEST_RESULTS_DIR` at a scratch directory it removes at exit, `UNITY_INSPECTOR_TOKEN_FILE` at a file in it that never exists (`NO_TOKEN_FILE`) and, through `setWslUsersRoot()` from a dynamic import made after those settings, the WSL users root at a directory in it that never exists (`NO_WSL_USERS_ROOT`), so the session running the tests never gives them an instance, a real command to run, a stage of its own, a live wrapper's claim file to write, or the real config home or `/mnt/c/Users` for the user's game's token and log searches to read. A file that wants one sets its own id and points the setting at a script from `test/support/stub-launcher.js` — `writeStubLauncher()` for the launcher (control files under the instances root drive its refusals, its `--args-help`, and whether its `--help` offers one; `useStubLauncher()` sets `STUB_INSTANCES_ROOT` and `STUB_STAGE_ROOT`, the two roots the stub reports in its list header and the only way the server learns where the test's instances and stages are) and `writeStubStopCommand()` for a user's-game stop — so no test can reach a real launcher or start a game. The stub launcher creates a missing instance itself, as the contract has it, and refuses one whose directory holds no `profile/`, so a test launching into an instance that already exists seeds it with `seedInstanceDir()`. **The Steam protocol launch is fenced off twice**, since it starts the user's real game: `session.js` points `BROFORCE_LAUNCH_CMD` at a no-op command (`NO_OP_LAUNCH_CMD`, which `useStubLauncher()` restores rather than deletes), and it sets `UNITY_INSPECTOR_TEST`, on which `resolveLaunchCommand()` throws rather than return the protocol launch. A test wanting its own launch command sets one; a unit test wanting the protocol launch's shape passes its own `env` object and only resolves it. **The port is fenced the same way**: `session.js` sets `UNITY_INSPECTOR_PORT` to `NO_LISTENER_PORT`, port 1, since unset the `steam` target falls back to 9999 and the tests would reach the user's running game, and every place that would clear the variable restores that value instead. **A test whose outcome turns on whether a game is running reads a fixed process table on Linux** — `setProcReader(fakeProcReader(...))` from `test/support/fake-proc.js` — since another session's game can start or stop between two reads of the real `/proc`; a test that must read the real one checks for a game before and after. `test/support/wrapper-harness.js` drives `wrapper.js` itself against `test/support/stub-child.js`. **Every fake mod answers the hello**: `startStubServer()` and `fakeInspector()` take a `hello` mode (`answerHello()` in `test/support/stub-server.js`: accept by default, `old-mod`, `{ protocol }`, `{ acceptAs }`, `refuse`, `silent`, `close`, or a function of the hello's params), settable between connections, record each connection's first line and every hello's params, and refuse a first line that is not a hello; a command handler never sees the hello.

## Architecture

```
Claude Code --stdio/MCP--> wrapper.js --stdio--> index.js --TCP:9999--> Unity Inspector Mod (C#) --> Unity Game
```

- `index.js` — the MCP server: tool schemas, the `handleToolCall()` switch, log resolution, the MCP resource. Starts the transport only when run directly, so tests can import from it
- `wrapper.js` — hot-reload proxy between Claude Code and `index.js`; injects the `restart_server` tool
- `lib/unity-client.js` — TCP client (`UnityInspectorClient`, `commandTimeout`), the connection handshake and the token search (`unityDataDirs()`, `steamTokenSearch()`, `readTokenFile()`), and `toolCommand()`, which maps a tool name and params to the mod command to send, the flag that chose it stripped
- `lib/game-process.js` — process detection, kill, launch, start time
- `lib/instance.js` — the instance derivation: the session id, the configured launcher, its launcher commands, and `withRoot()`, which hangs the instance's paths off the roots the launcher reported
- `lib/command-line.js` — `tokenizeCommand()`, shared by every setting that holds a command plus arguments
- `lib/script-library.js` — C# script library and JSON test scripts
- `lib/log-delta.js` — what the target's two logs gained during a `run_test_script` run, grouped by source
- `lib/animation-capture.js` — the animation-capture sweep `capture_animations` drives: the state-list merge, the level and swap waits, the sentinel wait and the report
- TCP JSON protocol: `{"id":"...","method":"...","params":{...}}\n` → `{"id":"...","success":true,"result":{...}}\n`. The first line on every connection is the hello, `{"method":"hello","params":{"token":...,"protocol":1}}`, and `connect()` resolves only once the mod accepted it (see Handshake). Responses route to their request by `id`; a reply arriving after its command timed out is dropped, never handed to the next command
- Env vars, all of them the `steam` target's and never an instance's: `UNITY_INSPECTOR_PORT` (default 9999, must match the mod's serverPort), `BROFORCE_LAUNCH_CMD` (how `launch_game` starts the user's game), `BROFORCE_STOP_CMD` (how `stop_game` stops it), `UNITY_INSPECTOR_LOG` (explicit log path), `UNITY_INSPECTOR_TOKEN_FILE` (explicit token file, authoritative: no search). `UNITY_INSPECTOR_TEST_RESULTS_DIR` overrides where `run_test_script` writes its full results. `UNITY_INSPECTOR_MCP_STOP_WAIT_MS` shortens the wrapper's shutdown wait for the tests, and `UNITY_INSPECTOR_MCP_CLAIM_FILE` is the path the wrapper hands its child to record the `owner.pid` it wrote
- **stdio carries the MCP protocol** — NEVER let a child process write to stdout

### Instances

- **Which instance**: `CLAUDE_SESSION_ID` names it. A session has an instance when the platform is Linux, the id matches `^[A-Za-z0-9_-]{1,64}$`, `BROFORCE_INSTANCE_CMD` names a launcher, and that launcher's `--help` names `instance <id>`; a malformed id is logged to stderr once and treated as absent, never thrown. Anything else means no instance and the server serves the user's game as it always has — never a refusal. `lib/instance.js` derives the id and the launcher commands; `withRoot()` turns that into `<root>/<id>/` and from it `profile/UMM/Core/Log.txt`, `home/unity3d/Free Lives/Broforce/` (`unityDataDir`, the game's Unity data folder) and its `Player.log`, `work/`, `game.pid`, `port`, `launch.log`, `owner.pid`, and the commands `<launcher> instance <id> launch|stop|remove` and `<launcher> instance list --json`, whose output is **JSON Lines** — a header object (the first with no `id`) carrying `instancesRoot` — the directory holding one directory per instance, and the only place the server learns it — `stageRoot` where the launcher reports one, and `cap` from a launcher that caps running instances (absent or null from one that does not, both read as no cap); the header's own `root` is the launcher's game root and is never read, then one object per instance directory (`id`, `running`, `pid`, `port`, `display`, `last_launch`, `stale`), which `summarizeInstanceList()` parses line by line, skipping any line that does not parse. The port is never derived and `--port` is never passed: the launcher allocates it and the server reads `port` back. **The launcher rewrites `port` on every launch, before `game.pid`** — a hard requirement of the contract, since the server accepts the file only when its mtime is at or after the spawn it is waiting on
- **Target**: the server holds one explicit target, `instance` or `steam`, in `index.js`. `resolveTarget()` settles it once — `instance` when the session has one, the probe passed and the root is known (`instanceTargetReady()`), else `steam` — and adopts a running instance as it does, so a server started beside one serves it without being told; only `launch_game` changes it after that (`steam: true` for the user's game, nothing for the instance). `activeConfig()` is what every detection, kill, log and launch call takes; `unityClient.pointAt({port, gameConfig, noPortMessage})` re-points the client and disconnects on a switch, `gameConfig` is what the crash detector inside `sendCommand` watches, and `noPortMessage` is what the connect stage says when the target has no port — `noPortMessage()` names the instance, so every tool fails with the same reason `pollUntilResponsive` gives. `launch_game` and `wait_for_game` are refused while a command is in flight, since both may drop the socket under it and it would be answered from whatever answers next. **The recorded `port` is used only while a game of ours is running** — `instanceOwnsGame()` (an owned process in the scan, or a validated pidfile), re-checked on every `pointClientAtTarget()`, since the launcher hands a freed port to whichever instance asks next and a stale number would run this session's commands inside somebody else's game; with no owned game the client has no port and commands say so
- **The launcher probe**: `--help` is the only question safe to put to a launcher that may have no instance mode — one without it takes any other first word for a profile name and launches the user's game. The verdict is the phrase `instance <id>` anywhere in its output of an exit-0 `--help`, so the program's own name is not part of the contract; the setting's leading arguments go to `--help` as to every other verb (`leadingArgs`). It runs once per process, started eagerly at startup so the MCP handshake does not wait on it, and commands await its verdict — but **only an answer settles it**: a `--help` that could not spawn, timed out or exited non-zero leaves `instanceModeChecked()` null and is asked again after the same 15s cooldown the root discovery has (`launchTiming.probeRetryMs`, and `forgetCommandHelp()` drops the memoized capture so the retry really runs it), while a `--help` that ran cleanly and does not name the phrase is final for the process — asking that launcher again would only hand `instance` to a program that reads it as a profile name. `restart_server` re-asks everything by being a new process. The `--help` run itself is `captureCommandHelp()` in `lib/game-process.js`, 5s and memoized per command line, so a program named in both `BROFORCE_INSTANCE_CMD` and `BROFORCE_LAUNCH_CMD` is asked once and its answer serves the probe and the argument channel alike; `resetInstanceModeProbe()` clears both memos for the tests
- **The instances root**: the launcher owns it and this repository hardcodes none. `discoverInstancesRoot()` in `index.js` runs `<launcher> instance list --json` once, after the probe has passed and never before — `instance` must not be handed to a launcher that has no instance mode — and reads `instancesRoot` from the header, plus `stageRoot` where the launcher reports one — the two roots `withRoot()` hangs `stagePath` and every instance path off; a header naming no `stageRoot`, or one that is not absolute, leaves the session with no stage at all, the non-absolute one dropped to null exactly as a non-absolute `instancesRoot` is. `withRoot()` then rebuilds both memoized configs, the instance's and the user's game's, so every path and the cwd rule alike come from that one answer. **Both the probe and the discovery run whenever `BROFORCE_INSTANCE_CMD` is set**, whatever `CLAUDE_SESSION_ID` says (`sessionLauncher()` is the launcher without an instance, `launcherRootKnown()` the two questions), since the instances root is also what keeps another session's game out of this server's `stop_game`; with no launcher configured the root is unknowable and every Broforce process counts as the user's, which the README says. Both run **on Linux only** (`setServerPlatform()` injects the platform for the tests), since instances are a Linux arrangement and off it nothing about the launch is this server's business. The list gets its own 4s budget and the probe's `--help` 5s, so the two together settle well inside the 15s takeover poll a replaced server's wrapper is sitting in. **A failure is remembered for 15s, not for the process's life** (`launchTiming.rootRetryMs`): the next caller past the cooldown asks again, since until the launcher answers the user's game cannot be told from another session's instance. A discovered root is `Object.assign`ed into the memoized configs rather than replacing them, so a config handed out before it was known — the client's `gameConfig`, a caller's local — gains it too; `stop_game` and `launch_game`'s restart still ask for the refusal before taking the config, since that call is what triggers the retry. A list that cannot be read, or one whose header names no absolute `instancesRoot`, means no instance: it is logged, the target falls back to `steam` exactly as a launcher without the mode does, and the reason reaches `game_state`'s `instanceReason` and `launch_game`'s reply alike — a launch that meant to start the instance and went to the user's game carries the same string. `instanceTargetReady()` is those two questions plus a session id of this server's own, and both `resolveTarget()` and `launch_game` go through it, since `setTarget()` can settle the target without any of them

- **Ownership**: a Broforce process is one whose `/proc/<pid>/comm` is `Broforce.x86_64`; one whose comm starts with `Broforce` and whose `argv[0]` basename matches `/^Broforce.*\.x86_64$/`, which is how a renamed copy of the binary with a bare argv is found; or one whose command line names `Broforce*.exe` and whose comm is a wine/proton form or a `Broforce`-prefixed name. `comm` truncates at 15 characters, so `Broforce_beta.exe` arrives as `Broforce_beta.e`. The Proton half of that rule is command-line only and has not been exercised against a live Proton launch. An instance owns the one whose `/proc/<pid>/cwd` is its `work/`; the user's game is any whose cwd is *not* under the instances root, and with no launcher to report that root, any at all. Every detection, start time and kill obeys this, so the two never see or stop each other
- **Launch on an instance**: a `restart` that could not stop the game (`unknown`, or survivors) launches nothing and reports the survivors. Whether a game is already running is the cwd rule's answer, never a ping — a ping answered on a recycled port is somebody else's game and must not refuse the launch. Preconditions first — a validated pidfile naming a live game refuses the launch (a listener on the instance's port does not, since the launcher reallocates a port whose listener is not this instance's game). Then the launch command is run and *waited out*, since only its exit carries the verdict and its port is written before it finishes. Exit 75 is a capping launcher's refusal at its cap: the server polls `<launcher> instance list --json` every 5s for up to 120s (its own budget, not the launch budget), relaunches on a free slot with a fresh 180s budget, and on expiry words four endings apart: a last readable list that was full (its ids are the slot holders), a last readable list the refusal disagreed with (reported as what the list showed, never as holders), a list unreadable on every attempt, and a budget spent before the list was ever checked; a readable list is kept as `runningInstances`. The last readable summary is carried across polls and across re-entries — one failed poll is one poll, and the wait that happens to end the loop says nothing about the polls before it. An unreadable list still counts as a freed slot and the launch is retried, as does a list reporting no cap — a launcher that caps nothing never holds a launch up. Any other non-zero exit is reported at once with the `launch.log` tail, or with the tail of the launcher's own stderr when there is no log yet — a launcher refusing a brand-new id has created nothing to write to. After a clean exit — and unless the launch was `vanilla`, which has no port and no inspector to wait for — the server waits up to 10s for a `port` file **written by this launch** — one whose mtime predates the spawn is an earlier run's allocation, which may since have gone to another instance — re-points the client and polls until the game answers. That freshly allocated port stands in for the length of that launch's own poll only, which the launcher's 180s reservation of a port it has just allocated makes safe; from the next command on the ownership gate applies as usual. A `port` that never appears is a `no-port` failure, worded differently for a launcher that had not finished and for a file the launch did not write, which the message dates. The failure tail is this launch's too: a `launch.log` older than the spawn is an earlier run's and gives way to the launcher's stderr. A polled launch's reply carries `instance: {id, port}`, the two log paths and `runningInstances`; a `vanilla` one has no port to report. A launch that finds the instance already running carries the same `instance` and `logs` fields, since the game it would have started is the one already there
- **Unplaceable instances**: while a launcher is configured and this server cannot place its instances — the `--help` went unanswered, or the mode is there and the root is not — every Broforce process reads as the user's, and `unplaceableInstancesReason()` in `index.js` is the one cause with two consequences. `steamKillRefusal()` wraps it for the kill: `killGame`'s `signalRefusal` returns `unknown: true` without signalling, so `stop_game` is a failure naming the reason. `launch_game` on the `steam` target asks the cause directly, before it decides whether a game is already running — a stranger's would read as the user's, broken — and answers `state: "root-unknown"` having launched and stopped nothing, `restart` included. Asking is also what drives both retries. `BROFORCE_STOP_CMD` still runs first when it is set, since it is the user's own tool and knows its own game; only the signal is this server's guess. Only a clean `--help` verdict of "no instance mode" lifts it, since that launcher runs no instances; with no launcher configured, or off Linux, there is nothing to protect and the kill runs as it always has. `instanceField()` awaits `launcherRootKnown()` before it reports anything, whatever this session's id says, so `game_state` drives both retries — for a session with no instance of its own too — and its `instanceReason` tells an unanswered `--help` from a launcher that answered and has no instance mode
- **Stop**: `stop_game` acts on the target only. With no game running, the user's game is left alone and no launcher is called — the reply says nothing was signalled — while an instance still goes through the launcher's stop — it tears the display down and clears the pidfile — and the reply says it tidied the instance up, answering `success: true` when that stop ran and exited 0, since the tidy-up is what the call asked for, and `false` when it could not run or exited non-zero. An instance is stopped with `<launcher> instance <id> stop` (20s budget), since that also tears its display down; a process still alive afterwards falls back to signalling, while a non-zero exit that left nothing running is still a stop and carries the exit status as a note — the targets are re-derived from a fresh `/proc` scan first — and the answer says which path stopped it. A running user's game goes through `BROFORCE_STOP_CMD` first (`userStopCommand()`, tokenized like every other command setting, the same 20s budget as the instance stop), verified by the ownership rule afterwards; a non-zero exit, a command that could not run, or a process still alive afterwards falls back to the same pid-scoped kill and says so, while a non-zero exit that left nothing running is still a stop with the exit status noted, and `launch_game { restart: true }` takes that same path. With the setting unset the pid-scoped kill is the whole of it. `BROFORCE_STOP_CMD` is a user's-game setting and is never consulted on the instance target. `remove: true` then runs `<launcher> instance <id> remove`; it is refused while the target is `steam`, and skipped with `removed: false` and the reason whenever the stop answered `unknown` or left survivors — `killGame` reports the pids that outlived it as `survivors`, since a stop that killed one of two processes is not a stop and deleting the directory would orphan the rest
- **The help channel**: `launchArgumentHelp()` renders `launch_game`'s description tail on every listing from two captures: `startLaunchHelpCapture()` of `BROFORCE_LAUNCH_CMD`, and `startInstanceHelpCapture()` of the instance launcher, taken only while `instanceTargetReady()` says a plain call runs the instance launch (own session id, instance mode, known root). Each runs `--help`, and `--args-help` only when that exited 0 and names it: an unknown flag might launch an unknown launcher's game. `argsHelpRecord()` memoizes per command line. A `--help` that could not answer is dropped with its `captureCommandHelp()` memo and re-asked by the next listing; a clean answer without the flag is cached for the process. Only the first listing waits, up to `ARGS_HELP_GRACE_MS` (1500ms), for readiness and the captures; later listings never wait. Until readiness first settles the tail only says help will follow; during a re-ask the last settled answer stands. `scheduleTailFollowUp()` re-renders when outstanding answers land and, if the tail changed, sends `notifications/tools/list_changed` (`listChanged: true` in capabilities, forwarded by `wrapper.js`): once per change, never before the first listing or while answers are outstanding, never thrown. `setToolListChangedNotifier()` is the test seam. One program in both settings with unlabelled output is one block; otherwise each launch has a section, instance first: a verbatim fenced block, a "publishes no argument help" line, or the Steam protocol launch's no-arguments line. `parseArgsHelp()` splits labelled output into per-launch sections by the contract's header rules. Each block is capped at 1KB in bytes, so the tail adds at most 2KB; `test/tool-list.test.js` measures the tool's own text, `test/launch-help.test.js` pins the worst-case tail
- **`owner.pid`**: `<root>/<id>/owner.pid` holds one line, `<pid> <starttime>` — `process.ppid` (the wrapper) and field 22 of its `/proc/<pid>/stat`, both decimal — and records only that this wrapper owns the id, never that a launch succeeded. `writeOwnerFile()` writes it before an instance launch command is spawned when the instance directory is already there, and otherwise as soon as the launcher has created it during that launch — `claimInstanceWhenCreated()` looks every 100ms for as long as the launch command runs, whatever the launch then ends as, and gives up when it ends with nothing there. The claim never creates the directory: the launcher creates a missing instance on its first launch, and a directory holding nothing but `owner.pid` reads to it as one that already exists. It is written at startup too, where `resolveTarget()` claims a running instance on the working-directory check alone, as soon as the root is known and before the client is pointed — the probe and the list that answer it take milliseconds, well inside the 15s the old wrapper waits — so a server reconnecting on `/mcp` wins the id before that wait runs out; `adoptRunningInstance()` then points the client at it. Every write also records the `owner.pid` path in `UNITY_INSPECTOR_MCP_CLAIM_FILE` when the wrapper named one, since the wrapper derives no root of its own. `stop_game` removes both once the stop left no survivors; the wrapper never does
- A stop by signal leaves the display the launcher created for the instance up; that is harmless and the next launch reuses it
- That fallback, and every stop of the user's game, prefers the validated `game.pid` — the pid's cwd must still match, and a pidfile that fails validation is deleted — and falls back to the scan. The pidfile is removed only once every target is gone, so a kill that failed leaves it in place. Nothing on Linux is ever killed by name
- A launch waits 180s, since setting an instance up (window, audio, port) outlasts a Steam launch. Failures carry the last 20 timestamped `launch.log` lines — the game's stdout lands in the same file, so untimestamped lines are dropped
- **The session's stage**: `game_state`'s `instance.stage` is the session's own `stagePath`, `<stageRoot>/<id>/UMM` off the stage root the launcher's list header reported — where this session builds, whatever the running game was composed from — and null from a launcher reporting no stage root
- `read_log` on an instance uses the two derived log paths and skips r2modman profile discovery entirely; `game_state` names them on every reply, alongside `target`, `port` (the target's own: 9999 or `UNITY_INSPECTOR_PORT` on `steam`, the instance's while a game of ours runs there, else null), `instance` and `runningInstances`
- Windows and macOS keep the name-based behaviour; instances are a Linux arrangement, and switching target leaves the other target's game running, which the launch reply says when that game is still up
- **No launcher is named anywhere in this repository**, CLAUDE.md included: the launcher is a setting, and `docs/launcher-contract.md` is what someone writing one implements

### Handshake

- **The token**: the mod writes `unity-inspector-<port>.token` (`tokenFileName()`) in the game's Unity `persistentDataPath` at every server start, before it listens. `#openSocket()` in `lib/unity-client.js` reads it after the TCP connect completes and before the hello, fresh on every connect, never cached; a completed connect means the file is current. Whitespace is trimmed, and with no file found the hello still goes out with `token: null`, so the mod's reply decides the message
- **Where**, by target, through the `tokenSearch` the client is pointed with (`pointClient()` in `index.js`, beside `gameConfig`): the instance looks in its own `unityDataDir` only, and `UNITY_INSPECTOR_TOKEN_FILE` never applies there. The user's game (`tokenSearch` null, the client's own `steamTokenSearch()`) takes `UNITY_INSPECTOR_TOKEN_FILE` as the file when set, else the newest-mtime readable candidate across `unityDataDirs()` — `$XDG_CONFIG_HOME/unity3d/...` when absolute, `~/.config/unity3d/...`, `$USERPROFILE` and `~` LocalLow, the Proton prefix's LocalLow, and on WSL every `/mnt/c/Users/*` LocalLow (`setWslUsersRoot()` is the tests' seam) — plus `~/Library/Application Support/Free Lives/Broforce`. `playerLogPaths()` builds its Player.log candidates from the same `unityDataDirs()`, so the two searches never drift; the macOS log roots and `<gamePath>/Broforce_Data` are log-only and Application Support token-only
- **Outcomes**: `handshakeOutcome()` turns the reply into `null` (accepted) or an error with `code` `HANDSHAKE_REFUSED` and `refusal` `old-mod` (`Unknown method: hello`), `protocol` (a top-level `protocol` beside the error, or an acceptance naming another protocol: when the mod's is higher the message says to update the server, and that a session whose server files are already updated loads them with `restart_server`; otherwise to update the mod) or `token` (any other refusal: the file it came from plus the mod's text, or with no file every directory searched, or the `UNITY_INSPECTOR_TOKEN_FILE` path). Each destroys the socket. `isHandshakeRefusal()` is the test. `HANDSHAKE_PROTOCOL` (1) is shared with the mod. Not refusals: a hello unanswered within the connect timeout (one budget covers connect and hello) is `code` `HANDSHAKE_TIMEOUT`, and a socket closed during it is the usual `Connection closed before it was established`; both carry `stage: 'handshake'`
- **Callers**: `pollUntilResponsive()` returns `handshake-refused` with the refusal's message on the first refusal, never retried to the deadline, and reads a `stage: 'handshake'` failure as the game having taken the connection — `connected-unresponsive` for the timeout, `connection-dropped`/`no-process` for a close. `launch_game`'s already-running check counts a refusal as a running game, answering `alreadyRunning: true, success: false, state: "handshake-refused"` and launching nothing; with `restart` it stops and relaunches as for any running game, and the relaunch's poll then reports the refusal. `sendCommand` maps only `ECONNREFUSED`, so a refusal reaches every tool, `capture_animations` included, as a tool error carrying its own message

### Hot Reload (wrapper.js)

- After editing `index.js` or anything under `lib/`, call `restart_server` instead of asking the user to `/mcp`. Editing `wrapper.js` itself does need a manual `/mcp` or Claude Code restart
- `restart_server` kills the child, respawns it, and replays the MCP `initialize` handshake. An unexpected child exit triggers the same sequence automatically; the third death within 30s stops respawning and requests get a JSON-RPC error until `restart_server` clears the lockout
- `UNITY_INSPECTOR_MCP_CHILD` / `UNITY_INSPECTOR_MCP_WRAPPER_LOG` let the tests drive the wrapper against a stub child
- **The wrapper's logger never throws** — a dead stderr, and a dead stdout, which only `sendToParent()` writes, are dropped silently rather than raised as errors, each noted once in the log file, so a shutdown that begins after the client took its pipes with it still runs to completion; twenty fatal reports within 5s exit the wrapper instead of a twenty-first
- **The wrapper stops the instance at session end**, since it is co-terminal with the session while the child is only what `restart_server` replaces. On stdin end, SIGTERM and SIGINT it reads its claim file — the path it passed the child as `UNITY_INSPECTOR_MCP_CLAIM_FILE`, holding the one line the server wrote there: the absolute `owner.pid` path — and then that `owner.pid`: no claim file, no owner file, an unreadable one (logged with the error's code) or one naming another pid, and the shutdown proceeds at once; naming its own pid and start time, it `spawnSync`s `instanceConfig()`'s own `instance <id> stop` command with stdio ignored under a 20s budget, logging how that command ended — a spawn that failed, a non-zero status or a signal, or a clean stop. **The trigger decides whether anything is waited out first.** Stdin end polls the file every 500ms for up to `UNITY_INSPECTOR_MCP_STOP_WAIT_MS` (default 15s) and stops only if it still names this wrapper at the end, so a server reconnecting on `/mcp` takes the id over; a client that closes stdin sends no signal afterwards, so the wait has the time. A signal stops on the one ownership read, no poll: a signalling client kills the process uncatchably under a second later. A signal arriving during a stdin-end poll cuts it short — the once-guard records the signal instead of swallowing it and wakes the sleeping poll tick rather than letting it run out, the loop breaks on it, ownership is re-read once, and the stop still runs at most once, however many signals arrive. It never removes `owner.pid`, it deletes its own claim file as it exits, and `restart_server` never reaches any of this. Every elapsed-time log line names its trigger — `after stdin end`, `after SIGTERM`, `after SIGINT` — the stop line and the wrapper's own exit line alike, so a real session end shows what grace period there was. The wrapper imports `lib/instance.js` and nothing else from `lib/`, and takes only the id and the stop command from it; `lib/instance.js` imports only `path` and `lib/command-line.js`, which is what keeps that true
- **id=0 gotcha**: MCP uses `id: 0` for init — check ids with `!== undefined && !== null`, never truthiness

### Adding a New MCP Tool

1. Tool definition (schema + description) in the `ListToolsRequestSchema` handler
2. `case` in the `handleToolCall()` switch
3. Game access: `result = await unityClient.sendCommand("method_name", params)`; a flag that picks a different mod command goes in `toolCommand()`, which `run_test_script`'s steps go through too
4. Node-only (file ops, process management): handle directly, no `sendCommand`
5. Matching handler in `BroforceMods/Unity Inspector Mod/Unity Inspector Mod/MessageHandler.cs`

### list_enemies

The tool is a thin `sendCommand`; everything below is the mod's `HandleListEnemies`.

- **The set**: the union of the game's own unit registry (`Map.units`) and a scene sweep of `NetworkedUnit`, since `Boss` derives from `NetworkedUnit` rather than `Unit` and sandworms never register. Duplicates are dropped by instance id. Entries are kept only when the GameObject is `activeInHierarchy` — `Map.units` holds inactive pre-spawned units, 52 face huggers on `Challenge_Alien` — and only when the game's own `IsEnemy` is true. `IsEnemy` means "not a hero and not a rescue bro", so neutral characters (villagers, citizens, animals) and a vehicle a player is currently piloting count, a tank's weapons are units of their own beside the tank, and a `BossTank` contributes dozens of `BossPiece` entries that all report the rig's origin as their position
- **`unitType` and `category`**: RocketLib classifies `Unit`/`TestVanDammeAnim`, so a `NetworkedUnit` that is neither reports both as null; a `Unit` RocketLib cannot classify reports `None`/`none`. `category` comes from a static dictionary built once from RocketLib's eight `UnitTypes` group arrays (`NormalUnits`, `AlienUnits`, `HellUnits`, `BossUnits`, `WormUnits`, `VehicleEnemies`, `FriendlyUnits`, `OtherUnits`) in that precedence — the arrays are disjoint, so precedence is only insurance. A type in no array reads `unknown`, which today is only `Bro`, and `IsEnemy` keeps that out of the list
- **Suppression**, reported only when the count is 0 and a level is loaded: `enemySpawnSuppressed`/`suppressedBy` assert a suppressor is active *right now* — Utility Mod loaded, enabled, and its `disableEnemySpawn` setting on, read by reflection through the mod's settings — so the level loaded with its enemies skipped rather than being empty. `enemySpawnPrefixOwners` is informational: every mod holding a Harmony prefix on the game's enemy placement or runtime spawn methods, `trace_spawns`' own excepted, i.e. who *could* suppress. A prefix may test its own settings before acting, so an owner there is no evidence anything was suppressed
- A response carrying `error` is a failed call — a main-thread timeout or an exception — and its `count`, `mapLoaded` and `enemies` are not observations of the level

### Tool notes

Behaviour the tool descriptions are too small to carry.

- **`game_state`**: the one gameplay scene is `Test Evan2` and the world map is `WorldMap3D`; `levelName` comes from the campaign file and is null on the challenge maps, which carry none, and `levelNumber` is the number `go_to_level`'s success message names; `isInGame` is false at the menu
- **`go_to_level`**: a `levelIndex` past the campaign's last level loads the Victory map, and the success message still names the level number that was asked for
- **`simulate_input`**: the 60-second plan limit totals a hold's `duration`, `count` presses with their `duration` and `interval`, or a `sequence`'s holds and waits. `highFive` throws back a live grenade within 20 units. `up`, `down`, `left` and `right` move and aim the bro; `fire` shoots the primary weapon; `jump` held with `down` drops through a platform; `sprint` runs; `gesture` plays the taunt; `start` opens the pause menu; `escape` backs out of menus
- **`wait_for_game`**: a timeout's `state` is `no-process` (no game process is running), `connection-refused` (the process is there but nothing is listening on the port), `connected-unresponsive` (the port accepts connections but the hello or ping got no reply), `connection-dropped` (the port accepted a connection that was then closed), `unknown` (process detection is unavailable) or `no-port` (this session's instance has no running game or port); `handshake-refused` (the mod refused the hello) ends the wait at once
- **`take_screenshot`**: a highlighted GameObject is outlined at its own renderer bounds, else its own collider bounds, else the combined bounds of its child renderers
- **`inspect_component` / `modify_component`**: `suggestions` are the closest paths, qualified with the prefix that resolved
- **`modify_component`**: `not-found` is no such field or property on the type, `read-only` one that exists with no setter or is a const field — readonly fields are written — and `error` a value that could not be converted, a setter that threw, or a dotted path that could not be walked: an empty segment, a `shared*` twin that would copy on read, an intermediate read that threw, or a null or destroyed intermediate
- **`spawn_entity`**: a failure on a missing prefab carries the resolved `unitType`. `Mook` units spawn alert, grounded and networked like level-placed enemies; `Facehugger` and `Screecher` go through the game's own local spawn helpers, so they are neither parented nor in the deterministic registry; every other unit is instantiated locally, parented to the map and registered, with `xI`/`yI` as its initial velocity. A mod suppressing enemy spawns (Utility Mod's `disableEnemySpawn`) fails a networked spawn, and the error names the patch owners. `ignoreSuppression` sets `disableEnemySpawn` false and restores it in the same main-thread action as the spawn, so the setting is never saved changed; `suppressionFound` is whether suppression was in force (Utility Mod enabled and the setting on), and null with a `suppressionNote` when Utility Mod or the setting is absent and the spawn ran unchanged
- **`swap_bro`**: `nextSpawn` reaches the mod as `set_bro`, whose reply is `nextBro`. `ignoreUnlocks` lifts Swap Bros Mod's IronBro unlocked-roster gate (`ignoreCurrentUnlocked`) and replaces its custom bro list with every installed custom bro, locked or disabled included (the names of BroMakerLib's `BroSpawnManager.GetAllBros()`), for the one swap, in one main-thread action, then restores both and every player's selection. `customBroCount` is set to BroMakerLib's unlocked count for the swap, which keeps Swap Bros Mod's list refresh from reloading its own list over that one. `ignoredUnlocks.rosterGate` is whether the gate was in force, `ignoreCurrentUnlocked` Swap Bros Mod's setting read back after the restore, `broFrom` where the swapped-in bro came from (`vanilla` for a name in its normal, Expendabros or unfinished rosters, `custom` for one in the custom list the swap used, null otherwise and on a failed swap), `customListReplaced` whether the list was replaced (`source` `GetAllBros`, else `unchanged`), and `note` why not (BroMakerLib absent or unreadable). The IronBro roster-gate half is verified by code trace only, with no IronBro run behind it. In IronBro a swapped-in bro the run has not collected that then dies is added to the run's `hardcoreModeDeadBros` by the game itself (`Player.RemoveLife`), exactly as Swap Bros Mod's own `ignoreCurrentUnlocked` option allows. Swap Bros Mod's own `enableBromaker` (off, its list never takes custom bros, so the replacement has no effect), its `filterBros` filter and its Expendabros/unfinished options still apply. `nextSpawn` with `ignoreUnlocks` is refused: the choice is read at the next spawn, after a restore would already have undone it
- **`trace_spawns`**: the mod installs one Harmony prefix per target at priority `int.MaxValue` under its own Harmony id, `<mod id>.trace-spawns`, so a prefix that skips the original cannot hide a call. Records: mooks `{seq, method, prefab, x, y, xI, yI, time}`, projectiles add `firedBy` (the firer's type name) and `playerNum`, doodads `{seq, method, doodadType, gridPosition: {x, y}, variation, time}`; `time` is `Time.realtimeSinceStartup`. `seq` is one counter across targets and never resets while the game runs. A `start` while tracing re-patches for the new set and keeps the records and the counter; a `start` with nothing traced clears the records; `stop` unpatches and clears them. The disconnect of the connection that started the trace unpatches it and keeps the records for `read`; a `start` or `stop` from any connection is honoured. The server keeps its socket across commands, and `wait_for_game`'s polls and `launch_game`'s already-running check reuse a live socket on an unchanged port rather than reconnecting. What drops it, and so ends a trace: `restart_server` (a new server process) always; a target switch; a change of the target's port, which includes an instance whose game is no longer ours and so has no port; `stop_game` and `launch_game` with `restart` or a fresh launch, which stop or replace the game anyway; and a socket the game closed

### Timeouts

`commandTimeout()` in `lib/unity-client.js`, keyed by mod command:
- default 6s — keep above the game's 5s `MainThreadDispatcher` budget
- `execute_script` / `compile_script` (the mod command `compileOnly` sends): 30s
- `execute_code`: 10s — keep above the mod's own 9s `execute_code` budget
- `unload_script`: 20s — keep above the mod's teardown, a 10s `Unload()` wait plus a 5s tracked-object destroy, so a timed-out stage's still-loaded refusal reaches the caller
- scene commands (`go_to_level`, `restart_level`, `swap_bro`, `set_bro` (the mod command `nextSpawn` sends), `take_screenshot`): 10s
- `simulate_input` with a non-empty `sequence`: the sum of each step's (duration ?? 50) + (wait ?? 0), + 1s, floored at the 6s default
- `simulate_input` with count > 1: (count − 1) × interval + count × (duration ?? 50) + 1s, floored the same way
- connect: 5s

### execute_code Contract

- Input compiles as its own block: statements, local declarations, a trailing `return expr;`, or a trailing expression as the value. Locals do not persist between calls, so state that must goes in static members or game objects; no lambda wrapping needed
- The tool result is the mod's own object, with three shapes on its top-level `success`: `resultSet:true` with `result`; `success:true, resultSet:false` for ran-but-void; `success:false` with `error`
- A failure from thrown user code also carries `position` (`{line, column}` of the top-level statement that was executing, 1-based in the submitted input) and `statement` (that statement's text). `position`, `statement` and `stackTrace` are all null for plain compiler diagnostics and for timeouts
- **Exceptions thrown by submitted code report `stackTrace`**, and reading `StackTrace` or `ToString()` is safe in `execute_code` input and inside a compiled script alike — a script's own `catch` gets a full managed trace naming its methods
- Types defined by a script loaded through `execute_script` are in scope for `execute_code`, by direct name and by reflection over the script assembly (field reads, member enumeration), consts and `null` consts included; an enum declared by a script or by `execute_code` is the exception, and `execute_code` input or a script naming one is refused before it compiles. `MethodBase.GetMethodBody()` on a script-compiled method kills the game process

### Crash Detection

`sendCommand` polls `isGameRunning()` for the target's own game — `unityClient.gameConfig`, set every time the client is pointed at a target — every 500ms while waiting and answers `"Game process died — the command likely caused a crash"` when the process disappears; when the socket closes first, the reply is `"Connection closed — game likely crashed"` instead. Death is declared only after the process was seen alive during that command; where detection is unavailable the command degrades to a normal timeout.

### Log Files

`resolveLogFile()` in `index.js` picks the file for `read_log`; every response carries `path` and `modifiedAt`.

- **Candidates**: `r2modmanPlus-local/Broforce/profiles/*/UMM/Core/Log.txt` under the r2modman config roots (profile names are arbitrary — glob, never hardcode); `Mods/UnityModManager/Log.txt` and `Mods/Log.txt` under the detected game path; the Unity player log (`Player.log` / `output_log.txt`) in every Unity data folder `unityDataDirs()` names (see Handshake), the macOS log roots, and `<gamePath>/Broforce_Data` — `playerLogPaths()` has the list. `Player-prev.log` is never a candidate
- `resolveLogFile()` resolves the running game's r2modman profile `Log.txt` first, falling back to the Unity player log paths (`Player.log` / `output_log.txt`) — the player log always exists and carries UMM's and every mod's output
- **Profile detection**: `detectActiveProfile()` looks for `profiles/<name>/` on the owned game's own command line, then in its environment (`run_umm.sh` passes the Doorstop target as `DOORSTOP_TARGET_ASSEMBLY`), then up the `ppid` chain — the wrapper consumes `--r2profile` and `run_umm.sh` consumes the Doorstop arguments, so the game's own argv usually carries neither. Two owned games resolving to different profiles is ambiguous and answers null, as a scan naming two profiles always has
- **Order**: `UNITY_INSPECTOR_LOG` is authoritative — a missing file there is the error, no fallback. Otherwise, with the game running and exactly one r2modman profile resolved: newest of that profile's `Log.txt`, then newest player log, both ignoring files last written before the game started; with no known start time the newest of profile and player logs wins outright. Anything else — game closed, ambiguous scan, non-r2modman launch, nothing written since start — takes the most recently modified candidate
- **Staleness**: `gameStartTime()` in `lib/game-process.js` (null when unavailable) minus a 3s tolerance is the cutoff; a chosen file predating it carries `stale: true` and a `warning`
- **The instance target** skips all of the above discovery: the candidates are the instance's own `profile/UMM/Core/Log.txt` and `home/unity3d/Free Lives/Broforce/Player.log`, in that order of preference, with the same staleness rules, and `UNITY_INSPECTOR_LOG` does not apply — so neither the not-found error nor the stale warning advises setting it there: the not-found error names the instance's two paths and says they appear once its game has started, and the stale warning names the remedy the chosen file allows: the player log carrying the same lines when the stale file is the profile log, and nothing fresher existing at all when the stale file is the player log itself. `targetLogPaths()` names both for `game_state` whether or not they exist
- **`read_log` with `onlyNew`**: 64KB per call, remainder flagged truncated. `isBaseline` is explicit on every read — `true`, with the last 20 lines, on the first call and whenever the file underneath changes, and `true` with no lines on `reset`: offsets key on `dev`+`ino` as well as path, so Unity rotating `Player.log` at launch rebaselines instead of slicing at the old offset, and the `path` can switch once mid-run to the profile log when UMM's log appears

### C# Script System (Node.js side)

- `scripts/csharp/` holds source-controlled `.cs` files; `parseScriptMetadata()` reads `// #name`, `// #description`, `// #tags`, `// #args` headers
- `list_scripts` is Node-only. It and `scripts://csharp/catalog`, the same catalog as an MCP resource, list every script; the tool list carries none of it, since every session start would pay for it
- `execute_script` reads the file in Node and sends **source** over TCP, never a path — the game may run under Proton with a different filesystem. With `compileOnly` it sends the mod's `compile_script`, whose reply is `types`, `hasMain` and `hasUnload`, or `compilerErrors` on a failure
- **Path safety**: absolute script paths are allowed; relative names must stay inside `scripts/csharp/`. A relative name with no such file resolves by the catalog's `#name`, case-insensitively, in `readScriptSource()`
- `list_test_scripts` / `run_test_script` cover `scripts/tests/`, the one directory holding every JSON test script; an absolute path runs a script from anywhere. The tool answers with `compactTestScriptReply()` over `runTestScript()`'s reply: that reply is written whole to `resultsFile` in `testResultsDir()` — `$XDG_STATE_HOME/unity-inspector-mcp/test-results`, else `~/.local/state/...`, never `os.tmpdir()`, which nix-shell deletes when the server exits — pruned to the newest 100 on each write; each step record shrinks to a 300-character `preview`, and the whole is shed level by level (passing previews, every preview, `logs`, the report's `events`/`stuck`/`survey` and other fields but `checks` over 2,000 characters, the whole `report`, the step lists), named in `omitted`, until it prints within 40,000 characters, since a larger MCP result is spilled to a file by the client. Steps dispatch straight to the game through `toolCommand()`, as the tools do, so `validateTestScriptSteps()` rejects Node-only tools as steps, whatever `toolCommand()` refuses, and `execute_script` steps giving neither or both of `params.path` and `params.source`. A `path` goes through `readScriptSource()` in `prepareTestScript()`, before anything runs, and the game is sent its source; the step's record keeps the `path`
- A step's optional `expect` (`success`, `contains`, `notContains`) decides whether it passed: with `expect` a step failing as expected passes and the run continues, and any unmet expectation fails the step with the unmet list as its `error`. `contains` matches substrings of the step result pretty-printed, the way the tools return it, or of the error message when the command threw. An `expect` naming none of the three, or one whose `contains`/`notContains` is empty, is rejected by `validateTestScriptSteps()` — it would pass a step whose command failed
- **The rest of a script's shape**, all settled in `prepareTestScript()` before a command is sent, so a bad script runs nothing: `{{name}}` placeholders in step and cleanup `params`, nested included, are filled from the call's `args` over the script's declared `args` defaults (`{default, description}` each, which `list_test_scripts` shows) — a string that is only the placeholder takes the arg's JSON type, and a placeholder with no value is a validation error naming it; `until: {timeout, interval}` (seconds, interval 1 by default, `expect` required) re-sends a step until its expect holds, sleeping `min(interval, time left)` so the last attempt lands at the deadline, stops early on a game-gone error, and records `attempts`, with `duration` covering every attempt; each attempt is an ordinary `sendCommand` under its own `commandTimeout()`; `report: true` lifts the step's `result` (execute_code's JSON string, or an object) into the reply's `report`, an array when several steps lift, and a result that is not a JSON object fails the step
- **Cleanup** runs after `steps` whatever ended them, unless the game is gone: the last step's thrown error with `isRunning()` answering false, or with it not answering true and the error being the client's crash or not-running message. A failed cleanup step never stops the rest; a game gone under one does, and `cleanupSkipped` says so. `passed` is every step and every cleanup step passed and no report's `passed` false. A script's `continueOnFailure: true` (boolean) records a failed step and runs on — a thrown one too, unless `gameGoneReason()` says the game is gone, which stops the steps and goes to cleanup — and adds `failures`, one `{step, command, error}` per failed step and cleanup step (`cleanup: true`), `error` being the first unmet expectation or the error's first line
- **`logs`**: `runTestScript()` snapshots `testScriptLogPaths()` after validation and attaches `collectLogDelta()`'s answer after cleanup on every path past it, failed steps and a dead game included. `testScriptLogPaths()` in `index.js` is `targetLogPaths()` except that an `UNITY_INSPECTOR_LOG` override named `Player.log`, `Player-prev.log` or `output_log.txt` is handed over as the player log rather than the UMM log. Before the read, when there is a UMM log and the game is not known to be gone, it waits `UMM_FLUSH_WAIT_MS` (600ms): UMM writes its buffer once more than 0.5s of game time has passed, summed from `Time.deltaTime` each `LateUpdate`, so under a time scale below 1 or a paused game the wait falls short and the last lines can be missing. A log whose `dev`+`ino` changed or that shrank is read from 0 and flagged `rotated`; one missing at the start is read whole; past 4MB a delta keeps its tail from a whole line and reports `skippedBytes`. Mod lines come from the UMM log by their first `[...]` prefix (`[Mod] [Script:x]` becomes `Mod › Script:x`, a `[Mod] Stack trace:` entry joins the one before it) and Unity log calls from Player.log's blocks ending `(Filename: ... Line: N)`, credited as `origin` to the first frame's root namespace outside the runtime, Unity and Harmony — `Broforce` for the game's un-namespaced types; Player.log's other unprefixed lines are `Unity (engine)`. Each log's copy of the other's lines (UMM's `[Unity]` mirror, Player.log's console copy of UMM) is dropped while the other is readable. Player.log's own `[Unity]` mirror lines are never counted, even with the UMM log unreadable, and a mirror's `red` or `yellow` colour sets the severity, `error` or `warning`, of the Unity call record below it. Messages group per source with stamps, frame counters, hex ids and digits normalized; a group of 50 or more is a flood, since a per-frame loop reaches that within a second while an ordinary line repeats a handful of times a run; only error, warning and flood groups are listed, with at most two variant samples; and the payload is shaped down level by level until it fits 12,000 characters (`truncated`, `omittedSources`, `omittedGroups`)
- **`capture_animations`** is server-side orchestration over `lib/animation-capture/animation-capture.cs` (`.claude/rules/animation-capture.md` is the reference), Node-only like `run_test_script`: `runCapture(options, unityClient, { sleep, pollMs, resolveLog, isRunning })` in `lib/animation-capture.js` sends every command through the server's own client, so the sweep follows the target. The handler validates the arguments — waits in seconds as `wait_for_game` takes them, an absolute `out` only ever cleared when an earlier sweep's `states.json` marks it, relative `states` names resolving inside `lib/animation-capture/states/` — and passes only `{ resolveLog: resolveLogFile }`, which is where a timeout's log tail comes from. A failure before the sweep is a thrown tool error; a sweep that ran answers `success`, `status` (`done`/`error`/`timeout`/`game-gone`), `message`, `report`, `paths`, `summary`, `stateErrors`, `swap` and `logTail`. The script and its state lists live under `lib/`, outside `scripts/` altogether, so `list_scripts`, its catalog resource and `list_test_scripts` never see them and this tool is what runs them
- **A sweep is server state.** `index.js` records it module-level for the sweep's whole length — the sentinel wait included, during which nothing is on the socket — and clears it in a `finally`, so a sweep that throws releases it. `refuseWhileInFlight()` consults that record before `inFlightCommands()`, so `launch_game`, `wait_for_game` and a second `capture_animations` are refused with a message naming the sweep, its `out` and the budget it has left; `stop_game` is deliberately let through, since the sentinel wait polls `isGameRunning` alongside the sentinel files and ends as `game-gone` within one poll, skipping the teardown rather than sending it to nothing
- **The signal teardown**: SIGINT and SIGTERM delegate to the exported `shutdownServer(signal, { exit })`, which runs the active sweep's `teardownGame` with each command budgeted at 800ms, gives the whole teardown 2s and then exits regardless, logging that the game may still be frozen. A sweep holds the game clock at zero with the capture script's patches installed, and the wrapper's `restart_server` sends SIGKILL 3s after its SIGTERM

### Game Process Management

- Everything lives in `lib/game-process.js`; nothing in the tool layer spawns processes directly
- **stdout is never piped from a spawn** — this process's stdout carries the MCP protocol. Spawns use `stdio: "ignore"` (or `runChild`'s piped capture) and an `error` handler; never `exec()` inheriting stdio. The one exception is the instance launcher's **stderr**, piped by `spawnDetached(..., { captureStderr: true })` so a launcher that refuses before it writes a `launch.log` can still say why: the stream is unref'd and only its last 4KB is kept. The user's game keeps its launcher's stdio closed, since the Steam client and the game would inherit the pipe and their chatter would read as launcher output
- **Ownership, not names** on Linux (see Instances): `isGameRunning`, `gameStartTime`, `killGame` and `detectActiveProfile` all take the target's config and go through `ownedGameProcesses()`, which scans `/proc` through an injectable reader (`createProcReader()`), so tests feed fake `/proc` data. Nothing on Linux ever kills or counts a Broforce process by name
- **Scan cache**: `scanGameProcesses()` memoizes for 750ms per reader, since the crash detector asks twice a second and a `/proc` walk costs tens of milliseconds. `killGame` clears it
- **Bracket trick** (macOS only, where there is no `/proc`): pgrep/pkill patterns bracket their first character *and* the extension (`[B]roforce.*[.]e[x]e`) so the wrapping `sh -c` command line can't match itself. Verify any new pattern with the game closed and confirm a non-zero exit
- `launch_game`: the target decides. On the instance target it is always `<launcher> instance <id> launch` from `BROFORCE_INSTANCE_CMD`; on the `steam` target `BROFORCE_LAUNCH_CMD` when set (parsed into command + args), otherwise a platform-appropriate Steam protocol launch of appid 274190. A configured launch command runs exactly as configured; the server adds no flag of its own beyond `--vanilla`. The command is resolved and checked for an executable — a regular file with `X_OK`, by path or through `PATH`, skipped on Windows — before a `restart` kills anything, so a launch that could not run leaves the running game alone. A `vanilla` launch is never polled, since Doorstop is off and no inspector will answer: it waits on the launch command's own exit — 45s on the user's game, and on an instance the same 180s budget and cap rules as any other launch, waited out once and reported as the budget actually spent — and reports a non-zero exit as a failure, with an instance's `launch.log` tail where there is one; past the budget the command is left running and said to be. Only the port readback and the inspector poll are skipped. A launch whose `--vanilla` was dropped, as the Steam protocol launch drops it, is polled like any modded launch instead. A launch command that exits non-zero ends the wait for either target; a clean exit is the normal hand-off for the user's game and the go-ahead to read `port` for an instance. Spawn failures come back as a tool error naming the command. A `launchArgs` string (tokenized shell-style) is appended to the launch the call runs; Steam protocol launches can't take it and say so
- `stop_game`: on Linux, `<launcher> instance <id> stop` for the instance target and `BROFORCE_STOP_CMD` for the user's game when that is set; otherwise, and whenever either command leaves the game running, SIGTERM to the owned pids and SIGKILL to whatever survives a 3s grace; `taskkill` on Windows, `pkill` on macOS. "Nothing matched" and "the tool is missing" are distinct results — the latter answers `unknown: true`
- `wait_for_game` and `launch_game`'s post-launch wait share `pollUntilResponsive()` in `index.js`: always at least one attempt, 60s/3s fallback for a non-finite or negative budget, and the call can overrun its deadline by the 5s connect timeout plus the 1s ping floor. Every attempt re-resolves the target's port through `pointClientAtTarget()`, so an instance whose game comes up mid-wait is picked up; with no port to be had the attempt and the final `no-port` state say so instead of guessing at a connection failure. A launch hands its own allocated port in as `launchedPort`, which stands in until the game it started is running and owns it. `connected-unresponsive` means only a ping-stage command timeout or an unanswered hello; a non-timeout failure at either is `no-process` when process detection confirms the game is not running, else `connection-dropped`. A handshake refusal ends the poll at once as `handshake-refused`
