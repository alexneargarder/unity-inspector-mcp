# Unity Inspector MCP Server

Node.js MCP server bridging Claude to the Unity Inspector Mod running inside Broforce.

**Test**: `nix-shell -p nodejs_22 --run "npm test"` — `node --test` executes every file under `test/`, so shared stubs live in `test-support/` instead. Every test file imports `test-support/session.js` first, before `index.js` or anything under `lib/`: it deletes `CLAUDE_SESSION_ID`, `BROFORCE_INSTANCE_CMD`, `BROFORCE_STOP_CMD` and `UNITY_INSPECTOR_MCP_CLAIM_FILE` and points `BROFORCE_LAUNCH_CMD` at a no-op command, so the session running the tests never gives them an instance, a real command to run, or a live wrapper's claim file to write. A file that wants one sets its own id and points the setting at a script from `test-support/stub-launcher.js` — `writeStubLauncher()` for the launcher (control files under the instances root drive its refusals, its `--args-help`, and whether its `--help` offers one; `useStubLauncher()` sets `STUB_INSTANCES_ROOT`, which is the root the stub reports in its list header and the only way the server learns where the test's instances are) and `writeStubStopCommand()` for a user's-game stop — so no test can reach a real launcher or start a game. The stub launcher creates a missing instance itself, as the contract has it, and refuses one whose directory holds no `profile/`, so a test launching into an instance that already exists seeds it with `seedInstanceDir()`. **The Steam protocol launch is fenced off twice**, since it starts the user's real game: `session.js` points `BROFORCE_LAUNCH_CMD` at a no-op command (`NO_OP_LAUNCH_CMD`, which `useStubLauncher()` restores rather than deletes), and it sets `UNITY_INSPECTOR_TEST`, on which `resolveLaunchCommand()` throws rather than return the protocol launch. A test wanting its own launch command sets one; a unit test wanting the protocol launch's shape passes its own `env` object and only resolves it. **The port is fenced the same way**: `session.js` sets `UNITY_INSPECTOR_PORT` to `NO_LISTENER_PORT`, port 1, since unset the `steam` target falls back to 9999 and the tests would reach the user's running game, and every place that would clear the variable restores that value instead. `test-support/wrapper-harness.js` drives `wrapper.js` itself against `test-support/stub-child.js`.

## Architecture

```
Claude Code --stdio/MCP--> wrapper.js --stdio--> index.js --TCP:9999--> Unity Inspector Mod (C#) --> Unity Game
```

- `index.js` — the MCP server: tool schemas, the `handleToolCall()` switch, log resolution, the MCP resource. Starts the transport only when run directly, so tests can import from it
- `wrapper.js` — hot-reload proxy between Claude Code and `index.js`; injects the `restart_server` tool
- `lib/unity-client.js` — TCP client (`UnityInspectorClient`, `commandTimeout`)
- `lib/game-process.js` — process detection, kill, launch, start time
- `lib/instance.js` — the instance derivation: the session id, the configured launcher, its launcher commands, and `withRoot()`, which hangs the instance's paths off the root the launcher reported
- `lib/command-line.js` — `tokenizeCommand()`, shared by every setting that holds a command plus arguments
- `lib/script-library.js` — C# script library and JSON test scripts
- TCP JSON protocol: `{"id":"...","method":"...","params":{...}}\n` → `{"id":"...","success":true,"result":{...}}\n`. Responses route to their request by `id`; a reply arriving after its command timed out is dropped, never handed to the next command
- Env vars, all of them the `steam` target's and never an instance's: `UNITY_INSPECTOR_PORT` (default 9999, must match the mod's serverPort), `BROFORCE_LAUNCH_CMD` (how `launch_game` starts the user's game), `BROFORCE_STOP_CMD` (how `stop_game` stops it), `UNITY_INSPECTOR_LOG` (explicit log path). `UNITY_INSPECTOR_MCP_STOP_WAIT_MS` shortens the wrapper's shutdown wait for the tests, and `UNITY_INSPECTOR_MCP_CLAIM_FILE` is the path the wrapper hands its child to record the `owner.pid` it wrote
- **stdio carries the MCP protocol** — NEVER let a child process write to stdout

### Instances

- **Which instance**: `CLAUDE_SESSION_ID` names it. A session has an instance when the platform is Linux, the id matches `^[A-Za-z0-9_-]{1,64}$`, `BROFORCE_INSTANCE_CMD` names a launcher, and that launcher's `--help` names `instance <id>`; a malformed id is logged to stderr once and treated as absent, never thrown. Anything else means no instance and the server serves the user's game as it always has — never a refusal. `lib/instance.js` derives the id and the launcher commands; `withRoot()` turns that into `<root>/<id>/` and from it `profile/UMM/Core/Log.txt`, `home/unity3d/Free Lives/Broforce/Player.log`, `work/`, `game.pid`, `port`, `launch.log`, `owner.pid`, and the commands `<launcher> instance <id> launch|stop|remove` and `<launcher> instance list --json`, whose output is **JSON Lines** — a header object (the first with no `id`) carrying `instancesRoot` — the directory holding one directory per instance, and the only place the server learns it — `stageRoot` where the launcher reports one, and `cap` from a launcher that caps running instances (absent or null from one that does not, both read as no cap); the header's own `root` is the launcher's game root and is never read, then one object per instance directory (`id`, `running`, `pid`, `port`, `display`, `last_launch`, `stale`), which `summarizeInstanceList()` parses line by line, skipping any line that does not parse. The port is never derived and `--port` is never passed: the launcher allocates it and the server reads `port` back. **The launcher rewrites `port` on every launch, before `game.pid`** — a hard requirement of the contract, since the server accepts the file only when its mtime is at or after the spawn it is waiting on
- **Target**: the server holds one explicit target, `instance` or `steam`, in `index.js`. `resolveTarget()` settles it once — `instance` when the session has one, the probe passed and the root is known (`instanceTargetReady()`), else `steam` — and adopts a running instance as it does, so a server started beside one serves it without being told; only `launch_game` changes it after that (`steam: true` for the user's game, nothing for the instance). `activeConfig()` is what every detection, kill, log and launch call takes; `unityClient.pointAt({port, gameConfig, noPortMessage})` re-points the client and disconnects on a switch, `gameConfig` is what the crash detector inside `sendCommand` watches, and `noPortMessage` is what the connect stage says when the target has no port — `noPortMessage()` names the instance, so every tool fails with the same reason `pollUntilResponsive` gives. `launch_game` and `wait_for_game` are refused while a command is in flight, since both drop the socket under it and it would be answered from whatever answers next. **The recorded `port` is used only while a game of ours is running** — `instanceOwnsGame()` (an owned process in the scan, or a validated pidfile), re-checked on every `pointClientAtTarget()`, since the launcher hands a freed port to whichever instance asks next and a stale number would run this session's commands inside somebody else's game; with no owned game the client has no port and commands say so
- **The launcher probe**: `--help` is the only question safe to put to a launcher that may have no instance mode — one without it takes any other first word for a profile name and launches the user's game. The verdict is the phrase `instance <id>` anywhere in its output of an exit-0 `--help`, so the program's own name is not part of the contract; the setting's leading arguments go to `--help` as to every other verb (`leadingArgs`). It runs once per process, started eagerly at startup so the MCP handshake does not wait on it, and commands await its verdict — but **only an answer settles it**: a `--help` that could not spawn, timed out or exited non-zero leaves `instanceModeChecked()` null and is asked again after the same 15s cooldown the root discovery has (`launchTiming.probeRetryMs`, and `forgetCommandHelp()` drops the memoized capture so the retry really runs it), while a `--help` that ran cleanly and does not name the phrase is final for the process — asking that launcher again would only hand `instance` to a program that reads it as a profile name. `restart_server` re-asks everything by being a new process. The `--help` run itself is `captureCommandHelp()` in `lib/game-process.js`, 5s and memoized per command line, so a program named in both `BROFORCE_INSTANCE_CMD` and `BROFORCE_LAUNCH_CMD` is asked once and its answer serves the probe and the argument channel alike; `resetInstanceModeProbe()` clears both memos for the tests
- **The instances root**: the launcher owns it and this repository hardcodes none. `discoverInstancesRoot()` in `index.js` runs `<launcher> instance list --json` once, after the probe has passed and never before — `instance` must not be handed to a launcher that has no instance mode — and reads `instancesRoot` from the header, plus `stageRoot` where the launcher reports one (carried on the config, unused so far). `withRoot()` then rebuilds both memoized configs, the instance's and the user's game's, so every path and the cwd rule alike come from that one answer. **Both the probe and the discovery run whenever `BROFORCE_INSTANCE_CMD` is set**, whatever `CLAUDE_SESSION_ID` says (`sessionLauncher()` is the launcher without an instance, `launcherRootKnown()` the two questions), since the instances root is also what keeps another session's game out of this server's `stop_game`; with no launcher configured the root is unknowable and every Broforce process counts as the user's, which the README says. Both run **on Linux only** (`setServerPlatform()` injects the platform for the tests), since instances are a Linux arrangement and off it nothing about the launch is this server's business. The list gets its own 4s budget and the probe's `--help` 5s, so the two together settle well inside the 15s takeover poll a replaced server's wrapper is sitting in. **A failure is remembered for 15s, not for the process's life** (`launchTiming.rootRetryMs`): the next caller past the cooldown asks again, since until the launcher answers the user's game cannot be told from another session's instance. A discovered root is `Object.assign`ed into the memoized configs rather than replacing them, so a config handed out before it was known — the client's `gameConfig`, a caller's local — gains it too; `stop_game` and `launch_game`'s restart still ask for the refusal before taking the config, since that call is what triggers the retry. A list that cannot be read, or one whose header names no absolute `instancesRoot`, means no instance: it is logged, the target falls back to `steam` exactly as a launcher without the mode does, and the reason reaches `game_state`'s `instanceReason` and `launch_game`'s reply alike — a launch that meant to start the instance and went to the user's game carries the same string. `instanceTargetReady()` is those two questions plus a session id of this server's own, and both `resolveTarget()` and `launch_game` go through it, since `setTarget()` can settle the target without any of them

- **Ownership**: a Broforce process is one whose `/proc/<pid>/comm` is `Broforce.x86_64`; one whose comm starts with `Broforce` and whose `argv[0]` basename matches `/^Broforce.*\.x86_64$/`, which is how a renamed copy of the binary with a bare argv is found; or one whose command line names `Broforce*.exe` and whose comm is a wine/proton form or a `Broforce`-prefixed name. `comm` truncates at 15 characters, so `Broforce_beta.exe` arrives as `Broforce_beta.e`. The Proton half of that rule is command-line only and has not been exercised against a live Proton launch. An instance owns the one whose `/proc/<pid>/cwd` is its `work/`; the user's game is any whose cwd is *not* under the instances root, and with no launcher to report that root, any at all. Every detection, start time and kill obeys this, so the two never see or stop each other
- **Launch on an instance**: a `restart` that could not stop the game (`unknown`, or survivors) launches nothing and reports the survivors. Whether a game is already running is the cwd rule's answer, never a ping — a ping answered on a recycled port is somebody else's game and must not refuse the launch. Preconditions first — a validated pidfile naming a live game refuses the launch (a listener on the instance's port does not, since the launcher reallocates a port whose listener is not this instance's game). Then the launch command is run and *waited out*, since only its exit carries the verdict and its port is written before it finishes. Exit 75 is a capping launcher's refusal at its cap: the server polls `<launcher> instance list --json` every 5s for up to 120s (its own budget, not the launch budget), relaunches on a free slot with a fresh 180s budget, and on expiry words four endings apart: a last readable list that was full (its ids are the slot holders), a last readable list the refusal disagreed with (reported as what the list showed, never as holders), a list unreadable on every attempt, and a budget spent before the list was ever checked; a readable list is kept as `runningInstances`. The last readable summary is carried across polls and across re-entries — one failed poll is one poll, and the wait that happens to end the loop says nothing about the polls before it. An unreadable list still counts as a freed slot and the launch is retried, as does a list reporting no cap — a launcher that caps nothing never holds a launch up. Any other non-zero exit is reported at once with the `launch.log` tail, or with the tail of the launcher's own stderr when there is no log yet — a launcher refusing a brand-new id has created nothing to write to. After a clean exit — and unless the launch was `vanilla`, which has no port and no inspector to wait for — the server waits up to 10s for a `port` file **written by this launch** — one whose mtime predates the spawn is an earlier run's allocation, which may since have gone to another instance — re-points the client and polls until the game answers. That freshly allocated port stands in for the length of that launch's own poll only, which the launcher's 180s reservation of a port it has just allocated makes safe; from the next command on the ownership gate applies as usual. A `port` that never appears is a `no-port` failure, worded differently for a launcher that had not finished and for a file the launch did not write, which the message dates. The failure tail is this launch's too: a `launch.log` older than the spawn is an earlier run's and gives way to the launcher's stderr. A polled launch's reply carries `instance: {id, port}`, the two log paths and `runningInstances`; a `vanilla` one has no port to report
- **Unplaceable instances**: while a launcher is configured and this server cannot place its instances — the `--help` went unanswered, or the mode is there and the root is not — every Broforce process reads as the user's, and `unplaceableInstancesReason()` in `index.js` is the one cause with two consequences. `steamKillRefusal()` wraps it for the kill: `killGame`'s `signalRefusal` returns `unknown: true` without signalling, so `stop_game` is a failure naming the reason. `launch_game` on the `steam` target asks the cause directly, before it decides whether a game is already running — a stranger's would read as the user's, broken — and answers `state: "root-unknown"` having launched and stopped nothing, `restart` included. Asking is also what drives both retries. `BROFORCE_STOP_CMD` still runs first when it is set, since it is the user's own tool and knows its own game; only the signal is this server's guess. Only a clean `--help` verdict of "no instance mode" lifts it, since that launcher runs no instances; with no launcher configured, or off Linux, there is nothing to protect and the kill runs as it always has. `instanceField()` awaits `launcherRootKnown()` before it reports anything, whatever this session's id says, so `game_state` drives both retries — for a session with no instance of its own too — and its `instanceReason` tells an unanswered `--help` from a launcher that answered and has no instance mode
- **Stop**: `stop_game` acts on the target only. With no game running, the user's game is left alone and no launcher is called — the reply says nothing was signalled — while an instance still goes through the launcher's stop — it tears the display down and clears the pidfile — and the reply says it tidied the instance up, answering `success: true` when that stop ran and exited 0, since the tidy-up is what the call asked for, and `false` when it could not run or exited non-zero. An instance is stopped with `<launcher> instance <id> stop` (20s budget), since that also tears its display down; a process still alive afterwards falls back to signalling, while a non-zero exit that left nothing running is still a stop and carries the exit status as a note — the targets are re-derived from a fresh `/proc` scan first — and the answer says which path stopped it. A running user's game goes through `BROFORCE_STOP_CMD` first (`userStopCommand()`, tokenized like every other command setting, the same 20s budget as the instance stop), verified by the ownership rule afterwards; a non-zero exit, a command that could not run, or a process still alive afterwards falls back to the same pid-scoped kill and says so, while a non-zero exit that left nothing running is still a stop with the exit status noted, and `launch_game { restart: true }` takes that same path. With the setting unset the pid-scoped kill is the whole of it. `BROFORCE_STOP_CMD` is a user's-game setting and is never consulted on the instance target. `remove: true` then runs `<launcher> instance <id> remove`; it is refused while the target is `steam`, and skipped with `removed: false` and the reason whenever the stop answered `unknown` or left survivors — `killGame` reports the pids that outlived it as `survivors`, since a stop that killed one of two processes is not a stop and deleting the directory would orphan the rest
- **The help channel**: when `BROFORCE_LAUNCH_CMD` is set, `startLaunchHelpCapture()` runs it with `--help` at startup — asynchronously, so the handshake never waits on it — and only when that output holds the literal `--args-help` does it run the command once more with that flag (`runCommandCapture()`, 10s, output capped at 1KB and marked when cut). An unknown launcher handed an unknown flag by name might launch the game, which is why the flag is confirmed by `--help` before it is used. `launchArgumentHelp()` turns the capture into the tail of `launch_game`'s description, rebuilt on every tool listing: the text quoted verbatim in a fenced block, or one line saying the command publishes no argument help and `launchArgs` pass through as given, or — with no launch command — that the Steam protocol launch takes no arguments
- **`owner.pid`**: `<root>/<id>/owner.pid` holds one line, `<pid> <starttime>` — `process.ppid` (the wrapper) and field 22 of its `/proc/<pid>/stat`, both decimal — and records only that this wrapper owns the id, never that a launch succeeded. `writeOwnerFile()` writes it before an instance launch command is spawned when the instance directory is already there, and otherwise as soon as the launcher has created it during that launch — `claimInstanceWhenCreated()` looks every 100ms for as long as the launch command runs, whatever the launch then ends as, and gives up when it ends with nothing there. The claim never creates the directory: the launcher creates a missing instance on its first launch, and a directory holding nothing but `owner.pid` reads to it as one that already exists. It is written at startup too, where `resolveTarget()` claims a running instance on the working-directory check alone, as soon as the root is known and before the client is pointed — the probe and the list that answer it take milliseconds, well inside the 15s the old wrapper waits — so a server reconnecting on `/mcp` wins the id before that wait runs out; `adoptRunningInstance()` then points the client at it. Every write also records the `owner.pid` path in `UNITY_INSPECTOR_MCP_CLAIM_FILE` when the wrapper named one, since the wrapper derives no root of its own. `stop_game` removes both once the stop left no survivors; the wrapper never does, since a stop that exited 0 while a launch was still in flight would otherwise leave an untracked game nothing reaps
- A stop by signal leaves the display the launcher created for the instance up; that is harmless and the next launch reuses it
- That fallback, and every stop of the user's game, prefers the validated `game.pid` — the pid's cwd must still match, and a pidfile that fails validation is deleted — and falls back to the scan. The pidfile is removed only once every target is gone, so a kill that failed leaves it in place. Nothing on Linux is ever killed by name
- A launch waits 180s, since setting an instance up (window, audio, port) outlasts a Steam launch. Failures carry the last 20 timestamped `launch.log` lines — the game's stdout lands in the same file, so untimestamped lines are dropped
- `read_log` / `watch_log` on an instance use the two derived log paths and skip r2modman profile discovery entirely; `game_state` names them on every reply, alongside `target`, `port` (the target's own: 9999 or `UNITY_INSPECTOR_PORT` on `steam`, the instance's while a game of ours runs there, else null), `instance` and `runningInstances`
- Windows and macOS keep the name-based behaviour; instances are a Linux arrangement, and switching target leaves the other target's game running, which the launch reply says when that game is still up
- **No launcher is named anywhere in this repository**, CLAUDE.md included: the launcher is a setting, and the README's contract section is what someone writing one implements

### Hot Reload (wrapper.js)

- After editing `index.js` or anything under `lib/`, call `restart_server` instead of asking the user to `/mcp`. Editing `wrapper.js` itself does need a manual `/mcp` or Claude Code restart
- `restart_server` kills the child, respawns it, and replays the MCP `initialize` handshake. An unexpected child exit triggers the same sequence automatically; the third death within 30s stops respawning and requests get a JSON-RPC error until `restart_server` clears the lockout
- `UNITY_INSPECTOR_MCP_CHILD` / `UNITY_INSPECTOR_MCP_WRAPPER_LOG` let the tests drive the wrapper against a stub child
- **The wrapper's logger never throws** — a dead stderr, and a dead stdout, which only `sendToParent()` writes, are dropped silently rather than raised as errors, each noted once in the log file, so a shutdown that begins after the client took its pipes with it still runs to completion; twenty fatal reports within 5s exit the wrapper instead of a twenty-first
- **The wrapper stops the instance at session end**, since it is co-terminal with the session while the child is only what `restart_server` replaces. On stdin end, SIGTERM and SIGINT it reads its claim file — the path it passed the child as `UNITY_INSPECTOR_MCP_CLAIM_FILE`, holding the one line the server wrote there: the absolute `owner.pid` path — and then that `owner.pid`: no claim file, no owner file, an unreadable one (logged with the error's code) or one naming another pid, and the shutdown proceeds at once; naming its own pid and start time, it `spawnSync`s `instanceConfig()`'s own `instance <id> stop` command with stdio ignored under a 20s budget, logging how that command ended — a spawn that failed, a non-zero status or a signal, or a clean stop. **The trigger decides whether anything is waited out first.** Stdin end polls the file every 500ms for up to `UNITY_INSPECTOR_MCP_STOP_WAIT_MS` (default 15s) and stops only if it still names this wrapper at the end, so a server reconnecting on `/mcp` takes the id over; a client that closes stdin sends no signal afterwards, so the wait has the time. A signal stops on the one ownership read, no poll: a signalling client kills the process uncatchably under a second later. A signal arriving during a stdin-end poll cuts it short — the once-guard records the signal instead of swallowing it and wakes the sleeping poll tick rather than letting it run out, the loop breaks on it, ownership is re-read once, and the stop still runs at most once, however many signals arrive. It never removes `owner.pid`, it deletes its own claim file as it exits, and `restart_server` never reaches any of this. Every elapsed-time log line names its trigger — `after stdin end`, `after SIGTERM`, `after SIGINT` — the stop line and the wrapper's own exit line alike, so a real session end shows what grace period there was. The wrapper imports `lib/instance.js` and nothing else from `lib/`, and takes only the id and the stop command from it; `lib/instance.js` imports only `path` and `lib/command-line.js`, which is what keeps that true
- **id=0 gotcha**: MCP uses `id: 0` for init — check ids with `!== undefined && !== null`, never truthiness

### Adding a New MCP Tool

1. Tool definition (schema + description) in the `ListToolsRequestSchema` handler
2. `case` in the `handleToolCall()` switch
3. Game access: `result = await unityClient.sendCommand("method_name", params)`
4. Node-only (file ops, process management): handle directly, no `sendCommand`
5. Matching handler in `BroforceMods/Unity Inspector Mod/Unity Inspector Mod/MessageHandler.cs`

### Timeouts

`commandTimeout()` in `lib/unity-client.js`:
- default 6s — keep above the game's 5s `MainThreadDispatcher` budget
- `execute_script` / `compile_script`: 30s
- `unload_script` / `execute_code`: 10s — keep above the mod's own 9s `execute_code` budget
- scene commands (`go_to_level`, `restart_level`, `swap_bro`, `set_bro`, `take_screenshot`): 10s
- `simulate_input` with a non-empty `sequence`: the sum of each step's (duration ?? 50) + (wait ?? 0), + 1s, floored at the 6s default
- `simulate_input` with count > 1: (count − 1) × interval + count × (duration ?? 50) + 1s, floored the same way
- connect: 5s

### execute_code Contract

- Input compiles as its own block: statements, local declarations, a trailing `return expr;`, or a trailing expression as the value. Locals do not persist between calls; no lambda wrapping needed
- The tool result is the mod's own object, with three shapes on its top-level `success`: `resultSet:true` with `result`; `success:true, resultSet:false` for ran-but-void; `success:false` with `error`
- A failure from thrown user code also carries `position` (`{line, column}` of the top-level statement that was executing, 1-based in the submitted input) and `statement` (that statement's text). `position`, `statement` and `stackTrace` are all null for plain compiler diagnostics and for timeouts
- **Exceptions thrown by submitted code report `stackTrace`**, and reading `StackTrace` or `ToString()` is safe in `execute_code` input and inside a compiled script alike — a script's own `catch` gets a full managed trace naming its methods
- Types defined by a script loaded through `execute_script` are in scope for `execute_code`, by direct name and by reflection over the script assembly (field reads, member enumeration). `MethodBase.GetMethodBody()` on a script-compiled method kills the game process

### Crash Detection

`sendCommand` polls `isGameRunning()` for the target's own game — `unityClient.gameConfig`, set every time the client is pointed at a target — every 500ms while waiting and answers `"Game process died — the command likely caused a crash"` when the process disappears; when the socket closes first, the reply is `"Connection closed — game likely crashed"` instead. Death is declared only after the process was seen alive during that command; where detection is unavailable the command degrades to a normal timeout.

### Log Files

`resolveLogFile()` in `index.js` picks the file for `read_log` and `watch_log`; every response carries `path` and `modifiedAt`.

- **Candidates**: `r2modmanPlus-local/Broforce/profiles/*/UMM/Core/Log.txt` under the r2modman config roots (profile names are arbitrary — glob, never hardcode); `Mods/UnityModManager/Log.txt` and `Mods/Log.txt` under the detected game path; the Unity player log (`Player.log` / `output_log.txt`) under each platform's Unity log root, the Proton prefix, and `<gamePath>/Broforce_Data` — `playerLogPaths()` has the list. `Player-prev.log` is never a candidate
- `resolveLogFile()` resolves the running game's r2modman profile `Log.txt` first, falling back to the Unity player log paths (`Player.log` / `output_log.txt`) — the player log always exists and carries UMM's and every mod's output
- **Profile detection**: `detectActiveProfile()` looks for `profiles/<name>/` on the owned game's own command line, then in its environment (`run_umm.sh` passes the Doorstop target as `DOORSTOP_TARGET_ASSEMBLY`), then up the `ppid` chain — the wrapper consumes `--r2profile` and `run_umm.sh` consumes the Doorstop arguments, so the game's own argv usually carries neither. Two owned games resolving to different profiles is ambiguous and answers null, as a scan naming two profiles always has
- **Order**: `UNITY_INSPECTOR_LOG` is authoritative — a missing file there is the error, no fallback. Otherwise, with the game running and exactly one r2modman profile resolved: newest of that profile's `Log.txt`, then newest player log, both ignoring files last written before the game started; with no known start time the newest of profile and player logs wins outright. Anything else — game closed, ambiguous scan, non-r2modman launch, nothing written since start — takes the most recently modified candidate
- **Staleness**: `gameStartTime()` in `lib/game-process.js` (null when unavailable) minus a 3s tolerance is the cutoff; a chosen file predating it carries `stale: true` and a `warning`
- **The instance target** skips all of the above discovery: the candidates are the instance's own `profile/UMM/Core/Log.txt` and `home/unity3d/Free Lives/Broforce/Player.log`, in that order of preference, with the same staleness rules, and `UNITY_INSPECTOR_LOG` does not apply — so neither the not-found error nor the stale warning advises setting it there: the not-found error names the instance's two paths and says they appear once its game has started, and the stale warning names the remedy the chosen file allows: the player log carrying the same lines when the stale file is the profile log, and nothing fresher existing at all when the stale file is the player log itself. `targetLogPaths()` names both for `game_state` whether or not they exist
- **`watch_log`**: 64KB per call, remainder flagged truncated. `isBaseline` is explicit on every read — `true` on the first call, on `reset`, and whenever the file underneath changes: offsets key on `dev`+`ino` as well as path, so Unity rotating `Player.log` at launch rebaselines instead of slicing at the old offset, and the `path` can switch once mid-run to the profile log when UMM's log appears

### C# Script System (Node.js side)

- `scripts/csharp/` holds source-controlled `.cs` files; `parseScriptMetadata()` reads `// #name`, `// #description`, `// #tags`, `// #args` headers
- `list_scripts` is Node-only. The `execute_script` tool description embeds the catalog, rebuilt on each `ListToolsRequestSchema` call; `scripts://csharp/catalog` exposes the same catalog as an MCP resource
- `execute_script` / `compile_script` read the file in Node and send **source** over TCP, never a path — the game may run under Proton with a different filesystem
- **Path safety**: absolute script paths are allowed; relative names must stay inside `scripts/csharp/`
- `list_test_scripts` / `run_test_script` cover `scripts/` and `scripts/examples/`. Steps dispatch straight to the game, so `validateTestScriptSteps()` rejects Node-only tools as steps, and `execute_script` / `compile_script` steps without inline `params.source`
- A step's optional `expect` (`success`, `contains`, `notContains`) decides whether it passed: with `expect` a step failing as expected passes and the run continues, and any unmet expectation fails the step with the unmet list as its `error`. `contains` matches substrings of the step result pretty-printed, the way the tools return it, or of the error message when the command threw. An `expect` naming none of the three, or one whose `contains`/`notContains` is empty, is rejected by `validateTestScriptSteps()` — it would pass a step whose command failed

### Game Process Management

- Everything lives in `lib/game-process.js`; nothing in the tool layer spawns processes directly
- **stdout is never piped from a spawn** — this process's stdout carries the MCP protocol. Spawns use `stdio: "ignore"` (or `runChild`'s piped capture) and an `error` handler; never `exec()` inheriting stdio. The one exception is the instance launcher's **stderr**, piped by `spawnDetached(..., { captureStderr: true })` so a launcher that refuses before it writes a `launch.log` can still say why: the stream is unref'd and only its last 4KB is kept. The user's game keeps its launcher's stdio closed, since the Steam client and the game would inherit the pipe and their chatter would read as launcher output
- **Ownership, not names** on Linux (see Instances): `isGameRunning`, `gameStartTime`, `killGame` and `detectActiveProfile` all take the target's config and go through `ownedGameProcesses()`, which scans `/proc` through an injectable reader (`createProcReader()`), so tests feed fake `/proc` data. Nothing on Linux ever kills or counts a Broforce process by name
- **Scan cache**: `scanGameProcesses()` memoizes for 750ms per reader, since the crash detector asks twice a second and a `/proc` walk costs tens of milliseconds. `killGame` clears it
- **Bracket trick** (macOS only, where there is no `/proc`): pgrep/pkill patterns bracket their first character *and* the extension (`[B]roforce.*[.]e[x]e`) so the wrapping `sh -c` command line can't match itself. Verify any new pattern with the game closed and confirm a non-zero exit
- `launch_game`: the target decides. On the instance target it is always `<launcher> instance <id> launch` from `BROFORCE_INSTANCE_CMD`; on the `steam` target `BROFORCE_LAUNCH_CMD` when set (parsed into command + args), otherwise a platform-appropriate Steam protocol launch of appid 274190. A configured launch command runs exactly as configured; the server adds no flag of its own beyond `--vanilla`. The command is resolved and checked for an executable — a regular file with `X_OK`, by path or through `PATH`, skipped on Windows — before a `restart` kills anything, so a launch that could not run leaves the running game alone. A `vanilla` launch is never polled, since Doorstop is off and no inspector will answer: it waits on the launch command's own exit — 45s on the user's game, and on an instance the same 180s budget and cap rules as any other launch, waited out once and reported as the budget actually spent — and reports a non-zero exit as a failure, with an instance's `launch.log` tail where there is one; past the budget the command is left running and said to be. Only the port readback and the inspector poll are skipped. A launch whose `--vanilla` was dropped, as the Steam protocol launch drops it, is polled like any modded launch instead. A launch command that exits non-zero ends the wait for either target; a clean exit is the normal hand-off for the user's game and the go-ahead to read `port` for an instance. Spawn failures come back as a tool error naming the command. A `launchArgs` string (tokenized shell-style) is appended; Steam launches can't take it and say so
- `stop_game`: on Linux, `<launcher> instance <id> stop` for the instance target and `BROFORCE_STOP_CMD` for the user's game when that is set; otherwise, and whenever either command leaves the game running, SIGTERM to the owned pids and SIGKILL to whatever survives a 3s grace; `taskkill` on Windows, `pkill` on macOS. "Nothing matched" and "the tool is missing" are distinct results — the latter answers `unknown: true`
- `wait_for_game` and `launch_game`'s post-launch wait share `pollUntilResponsive()` in `index.js`: always at least one attempt, 60s/3s fallback for a non-finite or negative budget, and the call can overrun its deadline by the 5s connect timeout plus the 1s ping floor. Every attempt re-resolves the target's port through `pointClientAtTarget()`, so an instance whose game comes up mid-wait is picked up; with no port to be had the attempt and the final `no-port` state say so instead of guessing at a connection failure. A launch hands its own allocated port in as `launchedPort`, which stands in until the game it started is running and owns it. `connected-unresponsive` means only a ping-stage command timeout; a non-timeout ping failure is `no-process` when process detection confirms the game is not running, else `connection-dropped`
